# muagba-pro

База окружения для мультиагентной разработки. Одна основа для всех проектов:
рамки, права, хуки, роли агентов и скилы настройки.

Репозиторий состоит из двух частей, и разделение между ними принципиальное:

| Часть | Что это | Как обновляется |
|---|---|---|
| `plugins/muagba-base/` | **Механика.** Хуки, роли, скилы. Одинакова везде. | Централизованно — обновление плагина прилетает во все проекты |
| `template/` | **Каркас.** Документы рамок и конфиги, которые проект заполняет под себя. | Копируется один раз и дальше живёт своей жизнью |

Механику, которая должна чиниться в одном месте, — в плагин. Содержание — в шаблон.

## Зачем это нужно

Один проверенный факт задаёт всю конструкцию. Сабагент получает в свой контекст:
собственный системный промпт, задачу, **всю иерархию `CLAUDE.md` и `AGENTS.md`**,
git status и предзагруженные скилы.

Он **не получает**: историю разговора, ранее прочитанные файлы, auto memory
ведущей сессии.

> Единственное, что разделяют все агенты проекта, — файловый слой. Договорённость,
> произнесённая в чате, для сабагента не существует. В одноагентной работе это
> неудобство; в мультиагентной — источник расхождений, которые всплывают на мерже.

Отсюда и состав базы: всё, что должно действовать на всех агентов, лежит в файлах,
а то, что обязано держаться всегда, — ещё и в хуках, потому что текст это просьба,
а не гарантия.

## Чего база не делает

У настройки есть конец. После Э11 база замолкает и живёт только хуками,
которые поставила.

**Конвейер разработки фич она не несёт.** Спеки, планы, нарезку задач и
проверку их формы делает тот плагин, который выбрал проект: Spec Kit,
OpenSpec, BMAD или своя форма. База объявляет к нему **интерфейс** —
`specs/README.md`, раздел «Конвейер фич», пять полей, — чтобы гейты и хуки
работали при любом выборе. Систему документации она тоже не подменяет: это
`docsys`. И работу с гитом не подменяет.

Правило, по которому проходит граница (`ADR-0009`): делается **один раз за
жизнь проекта** — это база; делается **на каждой фиче** — это чужой плагин, и
база его подключает. Почему конвейер фич чужой — `ADR-0010`; почему проба
проверяет свойство проекта, а не наш файл, — `ADR-0011`.

## Установка

### 1. Плагины

Ставится один. `docsys` приезжает сам: он объявлен зависимостью
`muagba-base`, потому что без него не закрываются этапы Э2–Э4 — документы
рамок это документы системы документации (`ADR-0001`).

```bash
/plugin marketplace add simbioz-team/muagba-pro
/plugin marketplace add simbioz-team/docsys
/plugin install muagba-base@muagba-pro
```

Второй маркетплейс регистрируется заранее, потому что зависимость живёт в
чужом каталоге, а Claude Code не добавляет чужие каталоги молча. Если строку
пропустить, установка не молчит: она скажет, что зависимость не разрешена, и
напечатает недостающую команду.

Локально, без публикации, — путь к своему клону:

```bash
/plugin marketplace add /path/to/muagba-pro
/plugin install muagba-base@muagba-pro
```

**Обновление.**

```bash
claude plugin marketplace update muagba-pro
claude plugin update muagba-base@muagba-pro
```

И **перезапустить сессию** — обновлённый плагин в текущей не подхватывается,
об этом же говорит сама команда: «restart required to apply».

Первая строка обязательна и неочевидна: Claude Code держит **копию** каталога
маркетплейса и без обновления просто не знает, что вышла новая версия. Это
верно и тогда, когда маркетплейс добавлен как локальная папка: кажется, что
раз каталог лежит на диске рядом, он читается на лету, — нет, он тоже
скопирован в кэш на момент добавления.

Сам плагин Claude Code считает свежим, пока не изменилась строка `version` в
его манифесте. Поэтому смотреть стоит на версию, а не на дату: текущая — в
[релизах](https://github.com/simbioz-team/muagba-pro/releases), что в ней
изменилось — в `CHANGELOG.md`. Что стоит сейчас, покажет `claude plugin list`.

Пока версия `0.x`, **минорный номер означает ломающее изменение**. Для базы
ломающим считается и появление новой проверки-гейта: формально это
добавление, фактически проект, который был зелёным, после обновления
краснеет. Так, `0.10.0` сделал семь проб строгими, и три обкатанных проекта
из 12/12 стали 7/12 и 8/12 — каждое покраснение оказалось настоящим дефектом,
который прежние пробы не видели.

**Ломающее обновление иногда требует дописать документ рамок, а он защищён.**
На проекте, где настройка уже закончена, защита включена (Э11), и правка идёт
по процедуре: снять строку из `.claude/protected-paths.txt`, дописать, вернуть
строку. При первичной настройке шага нет — защита включается позже, чем
спрашиваются эти разделы. Что именно дописать, перечислено в `CHANGELOG.md`
разделом «Миграция» у той версии, которая этого потребовала.

### 2. Настройка

Открой сессию в каталоге проекта — пустом или уже существующем — и запусти:

```
/muagba-base:setup-project
```

Дальше делать руками нечего. **Каркас разворачивает сам плагин** на Э0:
`git init`, копирование шаблона, первый коммит. Путь к шаблону он находит сам
через записи маркетплейсов Claude Code, так что помнить, куда склонирован
репозиторий, не нужно.

**На непустом проекте ничего не перезаписывается.** В каркасе лежат
`CLAUDE.md`, `README.md`, `AGENTS.md` и `.gitignore` — имена, которые в живом
репозитории уже заняты. Копирование идёт без затирания: занятые имена
пропускаются, а скил показывает список совпадений и разбирает их с тобой по
одному. Свод правил и `.gitignore` сводятся, а не заменяются.

Пустая папка — штатное начало, а не особый случай: конвейер отвечает и там,
где нет ещё ни `.git`, ни `.claude/`, и говорит, что следующий этап Э0.

Дальше он проводит по этапам Э0–Э11: спрашивает по банку вопросов, разбирает
уже готовое продуктовое описание, проверяет каждый этап пробами и не идёт
дальше, пока этап не закрылся. Прерывается в любой момент и продолжает с
места остановки.

Сессию нужно открывать **в каталоге самого проекта**. Настройка со стороны
выглядит работающей и из соседнего каталога, но держится на честном слове:
рабочие деревья сабагентов ответвляются от проекта сессии, журнал агентов
пишется туда же. Скил это проверяет и останавливается.

## Что даёт плагин

**Хуки** — то, что работает детерминированно, независимо от контекста агента:

| Событие | Скрипт | Что делает |
|---|---|---|
| `PreToolUse` (Edit/Write) | `protect-paths.sh` | Блокирует правку путей из `.claude/protected-paths.txt`; шаблон с префиксом `+` разрешает создать файл и запрещает изменить созданный |
| `PreToolUse` (Bash) | `guard-bash.sh` | Блокирует `rm -rf /`, force-push, `reset --hard`, `clean -fd`, `chmod 777`, а также запись в защищённый путь через оболочку — в том числе внутри `if`, циклов, `{ … }`, `( … )`, `$( … )`, `case` и на любой строке многострочной команды: перенаправление, `tee`, `sed -i`, `cp/mv`, `dd`, запись из `python3 -c` и heredoc'а. Туда же удаление: `rm` защищённого пути запрещён, `rm` файла, которого нет в гите и который не пересобирается, — спрашивает человека. Относительные цели достраивает от пройденного в той же команде `cd` |
| `Stop` | `gate-check.sh` | Не даёт закрыть ход, пока `.claude/check.sh` красный. Остановку ради вопроса отпускает — с предупреждением человеку, что проверка красная |
| `SubagentStop` | `gate-check.sh` | Тот же гейт для исполнителя (`implementer`); остальные роли код не правят и не держатся |
| `PostToolUse` | `journal_watch.py tick` | Контекст вырос на `MUAGBA_JOURNAL_EVERY` токенов (150 000) с последней записи `docs/journal/` — напоминает агенту обновить журнал сессии. Сабагентам не напоминает |
| `PostCompact` | `journal_watch.py postcompact` | Сохраняет выжимку сжатия в `docs/journal/raw/` |
| `SessionStart` (compact) | `reinject-invariants.sh` | Возвращает `.claude/invariants.md` в контекст после компакции |
| `SessionStart` (compact) | `journal_watch.py reinject` | Называет последнюю запись журнала и велит перечитать её и продолжить |
| `SubagentStart/Stop` | `log-agent.sh` | Журнал запусков в `.claude/logs/agents.jsonl` **проекта сессии** |

Защита путей определяет проект **по самому файлу**, а не по каталогу сессии:
правила на файл накладывает тот проект, в котором он лежит. Журнал агентов —
наоборот, по сессии: сабагент принадлежит той сессии, которая его запустила,
даже если работает в соседнем каталоге. Знать эту разницу стоит тому, кто
держит несколько репозиториев из одной сессии.

**Чем защита путей является и чем не является.** Список читается из того
checkout'а, где идёт правка: в рабочем дереве копия своя, и снятие строки там
открывает файл только в этом дереве. Сам `.claude/protected-paths.txt` в
собственном списке не значится — иначе агент не смог бы включить защиту на
Э11, где он её и включает. И процедура правки документов рамок прямо
разрешает агенту выполнять шаги по явной просьбе человека.

Значит это **порог с отметкой в истории, а не стена.** Он не даёт снять
запрет походя и оставляет след, если снимали. От агента, которому велели
снять запрет, он не защищает и не должен. Переоценённая защита опаснее
названного предела: на неё начинают полагаться там, где она не работает.

Все хуки — no-op, если проект не завёл соответствующий файл. Базу можно ставить
на любой проект без подготовки.

**У защиты команд есть предел, и его стоит знать.** Разбор статический:
путь, вычисленный внутри скрипта, он не получит — это предел подхода, а не
пробел в регулярке. Поэтому там, где запись есть, а цель не читается,
защищённые пути сверяются **по тексту самой команды** со снятыми кавычками:
`Path(x)/"docs"/"workflow.md"` ловится как `docs/workflow.md`. Плата —
ложные срабатывания: скрипт, который лишь упоминает защищённый файл и пишет в
другой, тоже будет остановлен. Правь такие файлы инструментом `Edit` или
вынеси путь в команду явным литералом.

Шаблон при этом сверяется **на границе пути**, а не как любая подстрока:
`.env` ловит `.env` и `.env.local`, но не `os.environ` и не
`src/environment.ts`. Без этого хук отвергал любой heredoc, читающий
переменные окружения, и исполнители теряли по два прогона, прежде чем
догадаться перейти на `Edit`.

**Удаление — отдельный случай, и решение там не всегда наше.** `rm`
защищённого пути запрещается наравне с правкой: удаление — самая необратимая
из правок, а до 0.14 защита смотрела только на запись, и
`rm docs/constitution.md` проходил насквозь. А вот `rm` файла, которого нет
в гите и который не похож на артефакт сборки, хук не запрещает, а
**спрашивает человека**: вернуть такой файл будет неоткуда — ни из истории,
ни пересборкой, — но ценны ли эти данные, знает только их владелец. Список
пересобираемых каталогов (`node_modules`, `dist`, `__pycache__`, …) заведомо
неполон, и это нормально: лишний вопрос стоит одного нажатия, пропущенное
удаление данных — всего. Поводом стал живой случай: агент одной цепочкой
`проверил && rm -f` снёс базу с данными заказчика, успев напечатать, сколько
в ней записей.

**Роли:** `implementer` (одна задача в изолированном дереве, коммит по
задаче), `reviewer` (свежий взгляд на дифф; проверяет поведением, а не
чтением, и ничего не правит), `researcher` (исследование в отдельном
контексте). Кого проект использует на самом деле — объявляется в
`docs/workflow.md`, раздел «Кто делает», и оттуда же берут пробы Э8.

**Скил:** `/muagba-base:setup-project`.

**Состояние настройки** — `scripts/setup_state.py`. Прогоняет пробы и говорит,
с какого этапа продолжать. Состояние не хранится, а выводится, поэтому
настройку можно прервать в любой момент:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/setup_state.py"          # таблица
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/setup_state.py" --json   # для скила
```

**Банк вопросов** — `questions/NN-*.md`, по файлу на этап. То, что конвейер
спрашивает у человека, записано, а не вспоминается на ходу. Вопросы Э2–Э4
собраны из литературы, остальные выведены из задач конвейера; у каждого есть
поле «Плохой ответ», дающее агенту право не принять ответ и назвать, чем он
плох. Устройство — `docs/interview.md`.

```
.gitignore                     + агентские записи
.worktreeinclude               что копировать в рабочие деревья
.env.example                   список переменных без значений
.mcp.json                      слот под MCP-серверы проекта
.github/workflows/ci.yml       гоняет тот же check.sh, что и Stop-хук
.claude/settings.json          права, слоты под маркетплейсы и плагины
.claude/protected-paths.txt    что нельзя править
.claude/invariants.md          что возвращать после компакции
.claude/check.sh               гейт завершения хода
.claude/check-frames.py        сканер незаполненных документов рамок
.claude/rules/                 правила, в т.ч. с paths-фронтматтером
.claude/agents/                слот под роли этого проекта

docs/tech-stack.md             чем делаем / что запрещено
docs/structure.md              раскладка и её принцип
docs/infrastructure.md         окружения, сервисы, секреты (удалить, если нет)
docs/workflow.md               рабочий цикл: откуда задача, кто делает и кто
                               проверяет, где живут задачи, ветки, откат
docs/toolchain.md              какие плагины включены и почему, когда вообще
                               что-то добавлять и что уже рассмотрено
docs/product/{mission,roadmap,glossary}.md
docs/decisions/                ADR
docs/lessons.md                выученное, ещё не ставшее правилом
docs/INDEX.md                  навигация: счётчики + таблица документов
docs/TAGS.md                   машинный индекс для поиска без чтения
specs/README.md                объявление конвейера фич + форма по умолчанию
```

**Конвейер разработки фич база не несёт** (`ADR-0010`). Его выбирает проект:
Spec Kit, OpenSpec, BMAD или своя форма. В `specs/README.md` проект объявляет
к нему интерфейс — пять полей, по которым гейт и хуки работают при любом
выборе: где лежат артефакты и как зовётся файл спеки; что значит «готова к
коду»; как задача ссылается на требование; кто и когда ставит готовность; чем
форма проверяется машинно. Последнее поле строгое: оно обязано называть
команду, и проба сверяет, что команда откуда-то вызывается.

Форма базы остаётся вариантом по умолчанию для тех, кто чужой конвейер не
берёт — со сценариями, доходящими до исхода, продуктовыми критериями приёмки
и сверкой с замыслом.

**Состояние задач живёт вне рабочего дерева.** У каждого дерева свой checkout:
незакоммиченная отметка «взял» в соседнее дерево не попадает вовсе,
закоммиченная остаётся в своей ветке. Файл в репозитории работает как доска
ровно для одного агента за раз. Где живёт общее состояние — записывается в
`docs/workflow.md` и проверяется пробой `roles.board` (`ADR-0008`).

### Реестры документации

`docs/INDEX.md` и `docs/TAGS.md` — точка входа в документацию: навигация для
человека и машинный индекс, по которому агент ищет, не читая документы подряд.
В шаблоне они пустые.

Собираются плагином [docsys](https://github.com/simbioz-team/docsys) — там же
семь команд `/doc-*` и четыре проверки документации. Он класс А: без него не
закрываются Э2–Э4. Реестры можно вести руками, но тогда
они разойдутся с документами; правило `.claude/rules/20-docs.md` задаёт контракт
метаданных независимо от плагина.

### Проверка заполненности

`.claude/check-frames.py` находит то, что осталось заготовкой: слоты `<...>`,
пустой раздел антицелей в `mission.md`, пустой список запрещённого в
`tech-stack.md`, глоссарий без терминов, принципы конституции без пометки
способа исполнения.

`check.sh` вызывает его в мягком режиме (`--soft`): новый проект не должен
краснеть только из-за пустых заготовок. На этапе Э11, когда рамки дописаны,
`--soft` убирается — и незаполненный слот начинает ронять проверку.

Живёт в шаблоне, а не в плагине: CI запускает `check.sh`, а в CI ни Claude Code,
ни плагина нет.

## Этапы настройки

Двенадцать этапов, 72 пробы. Подробно — `docs/pipeline.md` (что и почему),
`docs/gates.md` (чем проверяется), `docs/interview.md` (что спрашивается).

| Блок | | Этап | Ключевая проба |
|---|---|---|---|
| Смысл | Э0 | Каркас и гигиена git | агентские записи в `.gitignore` |
| | Э1 | Точка входа для агентов | свод правил ≤ 200 строк |
| | Э2 | Продуктовая рамка | раздел антицелей непуст |

| Принуждение | Э7 | Принудительные рамки | синтетический вызов хука даёт 2 |

**Э6 — граница.** Параллельных агентов до неё не запускать: без исполнимой
проверки агент останавливается на «выглядит готово», и верификатором становится
человек, который за несколькими агентами не успевает.

## Сторонние плагины

Два класса, и различаются они не составом, а тем, кто и когда решает
(`ADR-0002`). **Класс А** — без него не закрывается гейт этапа; сегодня это
`muagba-base` и `docsys`, ставятся молча. **Класс Б** — обвязка проекта;
выбирает человек, по сработавшему триггеру, с записанным условием снятия.

Прежде чем писать своё, смотрим, есть ли готовое: встроенное в Claude Code,
в официальном маркетплейсе, у сообщества (`ADR-0007`). Порядок разведки,
критерий «живое чужое» из пяти пунктов, таблица триггеров и список уже
рассмотренных кандидатов с известными конфликтами — в `docs/toolchain.md`;
каркас несёт свою копию, чтобы проект не искал заново.

Слот под установку — `extraKnownMarketplaces` и `enabledPlugins` в
`template/.claude/settings.json`.
