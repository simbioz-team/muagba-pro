# Э3. Конституция и «готово» — вопросы

Принципы выводятся из того, что за продукт: «Test-First обязателен» осмысленно
для библиотеки и бессмысленно для разведочного прототипа. Поэтому этап идёт
после Э2, а не до.

Требования к формулировке взяты из шаблона конституции GitHub Spec Kit:
принцип должен быть **декларативным, проверяемым и без расплывчатых слов**.

### В3.1 Что в этом проекте нельзя нарушать, даже когда это удобно

**Заполняет:** `docs/constitution.md` → «Принципы»
**Спрашивать:** всегда
**Зачем:** 5–9 правил, которые агент не нарушает без разговора с человеком.
Больше девяти не запоминается и не соблюдается — свод превращается в шум.
**Плохой ответ:** расплывчатая формулировка: «код должен быть качественным»,
«следуем лучшим практикам». Проверить нельзя, значит нарушить нельзя, значит
это не принцип. И отдельно: «should» вместо «must» — если на самом деле
нельзя, так и пишем.
**Источник:** GitHub Spec Kit, `constitution.md`: «declarative, testable, and
free of vague language».

### В3.2 Почему каждый из них принцип, а не пожелание

**Заполняет:** `docs/constitution.md` → обоснование внутри принципа
**Спрашивать:** всегда
**Зачем:** принцип без обоснования снимут при первом же неудобстве — нечего
противопоставить аргументу «сейчас проще так». Обоснование и есть то, что
переживает спор.
**Плохой ответ:** обоснование, повторяющее формулировку другими словами.
**Источник:** GitHub Spec Kit: «explicit rationale if not obvious».

### В3.3 Какие из принципов вы готовы принуждать машиной

**Заполняет:** `docs/constitution.md` → строка `Исполнение:` у каждого принципа
**Спрашивать:** всегда
**Зачем:** отделить то, что держится хуком или правом, от того, что держится
вниманием человека. Принцип без пометки — самообман: текст в документе это
просьба, а не гарантия.
**Плохой ответ:** пометить «машинно» всё подряд. Это обещание, которое
придётся выполнить на Э7; невыполненное — `const.enforced` не подтвердится, и
Э3 останется открытым задним числом.
**Источник:** задача З3.2.

### В3.4 Что агенту запрещено делать без разговора с человеком

**Заполняет:** `docs/constitution.md` → «Ограничения»
**Спрашивать:** всегда
**Зачем:** граница самостоятельности. Список отсюда превращается в `ask` и
`deny` на Э7.
**Плохой ответ:** запрет, сформулированный как намерение («не менять
архитектуру необдуманно»). Нужно действие, которое видно со стороны:
«не добавлять зависимость», «не менять схему базы», «не трогать CI».
**Источник:** задача З3.1.

### В3.5 Какие технические требования диктует характер продукта

**Заполняет:** `docs/constitution.md` → «Ограничения»
**Спрашивать:** всегда
**Зачем:** нефункциональные требования обычно всплывают в момент, когда их
уже нарушили. Удобное оглавление — характеристики качества ISO/IEC 25010:
функциональная пригодность, надёжность, производительность, безопасность,
совместимость, сопровождаемость, переносимость, удобство взаимодействия.
Пройтись по списку и отметить, где у продукта есть реальное ограничение.
**Плохой ответ:** требование без метрики и порога: «должно быть быстро».
У требования есть величина, порог и способ проверки — иначе на Э6 его нечем
превратить в тест.
**Источник:** ISO/IEC 25010 как оглавление нефункциональных требований.

### В3.6 Что должно быть верно сверх базового списка, чтобы задача считалась сделанной

**Заполняет:** `docs/definition-of-done.md` → пункт «проектные пункты»
**Спрашивать:** всегда
**Зачем:** базовые шесть пунктов шаблона одинаковы для всех проектов.
Проектное — миграции, документация API, обновление словаря — знает только
команда.
**Плохой ответ:** пункт, который нельзя подтвердить выводом команды или
чтением диффа. «Готово» — короткий измеримый список, всё остальное живёт в
конституции.
**Источник:** Scrum.org, Definition of Done: короткий измеримый список,
заводится до первой итерации.

### В3.7 Чего «готово» сознательно не означает

**Заполняет:** `docs/definition-of-done.md` → «Чего „готово" не означает»
**Спрашивать:** всегда
**Зачем:** зеркало антицелей, только для процесса. Ловит два типовых провала
агента: остановку на «выглядит правильно» и попутный рефакторинг соседнего
кода.
**Плохой ответ:** пусто. Раздел в шаблоне уже заполнен двумя пунктами; вопрос
про третий, свой.
**Источник:** задача З3.3.

### В3.8 Кто и каким действием меняет конституцию

**Заполняет:** `docs/constitution.md` → «Изменение конституции»
**Спрашивать:** всегда
**Зачем:** конституция, которую агент меняет по ходу дела, — не конституция.
Раздел отвечает, кто вносит поправку, что при этом обязательно происходит и
как отличить уточнение формулировки от смены правила.
**Плохой ответ:** «обсудим». Порядок без именованного действия — не порядок.
Рабочая форма берётся из Spec Kit: смена или удаление принципа — крупное
изменение, добавление — среднее, уточнение формулировки — мелкое; версия
и дата поправки проставляются в самом документе.
**Источник:** GitHub Spec Kit, семантика версий конституции.
