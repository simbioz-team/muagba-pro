# muagba-pro — база агентского окружения

Это не обычный проект: здесь нет прикладного кода. Репозиторий содержит
**механику** (плагин `plugins/muagba-base/`) и **каркас** (`template/`),
которые копируются и устанавливаются в другие проекты.

## Раскладка

- `plugins/muagba-base/` — плагин: хуки, роли, скилы, банк вопросов
  (`questions/`). Меняется централизованно.
- `template/` — то, что копируется в новый проект. **Это заготовки со слотами,
  а не рабочие документы.** Не заполняй их содержанием конкретного проекта.
- `.claude-plugin/marketplace.json` — репозиторий как маркетплейс.

## Правила работы над базой

- Хук обязан быть **no-op, если проект не завёл нужный файл**. База ставится на
  любой проект без подготовки — это её главное свойство, не ломай его.
- Хуки читают рабочую директорию из поля `cwd` входного JSON, а не из
  `${CLAUDE_PROJECT_DIR}`: в worktree-сессии второе остаётся на основном
  checkout, и проверка уйдёт не туда.
- Зависимости хуков — только `bash`, `git`, `python3`. Ни `jq`, ни чего-то
  ещё: база копируется на чужие машины.
- Права на запись сверяются только с `Edit(...)`. Правило `Write(...)`,
  `NotebookEdit(...)`, `MultiEdit(...)` или `Glob(...)` принимается, но
  никогда не консультируется.
- `exit 2` в хуке блокирует действие независимо от JSON на stdout и сильнее
  любого allow-правила.
- Меняешь состав хуков или ролей — обнови таблицы в `README.md`.
- Меняешь поведение хука — допиши случай в `plugins/muagba-base/scripts/tests/`.
  Файл случаев, который никто не прогоняет, ничего не ловит: так и вышло с
  `rm_cases.tsv` между 0.1.1 и 0.2.0.
- Добавляешь вопрос в банк — он обязан что-то заполнять, и это что-то обязана
  проверять проба. Вопрос без цели — беседа, проба без вопроса — дыра.

## Проверка после правок

```bash
bash -n plugins/muagba-base/scripts/*.sh
python3 -c "import json,glob;[json.load(open(f)) for f in glob.glob('**/*.json',recursive=True)]"
bash plugins/muagba-base/scripts/tests/run.sh
```

## Релиз

Версия плагина в `plugin.json` **пинит** его для тех, кто ставит с GitHub: пока
строка та же, Claude Code считает плагин свежим и оставляет пользователю
закэшированную копию. Забыли поднять — изменения не доехали, и никто этого не
заметит.

Порядок:

1. Поднять `version` в `plugins/<имя>/.claude-plugin/plugin.json`.
2. Дописать раздел в `CHANGELOG.md`.
3. Закоммитить, запушить.
4. `claude plugin tag plugins/<имя> --push -m "<имя> %s"` — создаёт тег
   `<имя>--v<версия>` и проверяет, что манифест плагина и запись в маркетплейсе
   не разошлись.
5. `gh release create <имя>--v<версия> --notes-from-tag` — чтобы версия была
   видна на GitHub, а не только в списке тегов.

Правило нумерации, пока `0.x`: **минор — ломающее, патч — всё остальное.**

Что ломающее для плагина:

- убрали или переименовали команду;
- во frontmatter появилось новое обязательное поле;
- несовместимо изменилась схема конфига;
- **добавили проверку-гейт** — формально это добавление, фактически проект,
  который был зелёным, краснеет после обновления.

Последний случай неочевиден и встречается чаще прочих. Смягчить можно
храповиком (как в проверке ссылок) или сделав проверку отчётом, а не гейтом
(как свежесть).

В PR это сторожит `.github/workflows/version.yml`: менялись файлы плагина, а
`version` нет — сборка краснеет.
## Чего не делать

- Не добавлять в `template/` файлы, специфичные для одного языка или стека.
  Каркас должен ставиться на Python, TypeScript и Go одинаково.
- Не наполнять `template/docs/*` реальным содержанием: там слоты.
- Не тянуть сторонние плагины внутрь базы — они ставятся в окружение и
  перечисляются в `docs/toolchain.md`.
