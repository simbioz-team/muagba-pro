# ADR-0015. Гейт хода — быстрый, полная проверка — перед слиянием

- **Дата:** 2026-10-01
- **Статус:** принято

## Контекст

До сих пор база держалась правила: `.claude/check.sh` — одна честная
проверка, её гоняет гейт хода (`Stop`, `SubagentStop`) и её же CI.

Проект narta на этапах 1.4–1.6 показал цену этого правила:

- 610 локальных прогонов `check.sh` за два этапа — 52,6 машино-часа,
  из них лишних — около 24 часов;
- полный прогон вырос с 2,5 до 13–18 минут: 4,6 тыс. тестов и до шести
  параллельных прогонов. Отсюда обрывы гейта по тайм-ауту, исполнители,
  снятые за зависание на ожидании фоновых прогонов, и общий файл
  покрытия, который портят параллельные прогоны в одном дереве;
- 82% красных ловили быстрые шаги — линтер, типы, документы, формы
  спек, — вместе около 45 секунд. Полный pytest дал 19 красных из 109.

Владелец narta решил: на гейте хода — только быстрые шаги, полные тесты
— перед слиянием и в CI.

## Решение

**1. Гейт хода может быть быстрым.** Гейт передаёт проверке, кто её
вызвал: `MUAGBA_GATE_EVENT=Stop|SubagentStop` (с 0.18.3). Проект решает
в своём `check.sh`, что гонять по этому событию. Не делить — законный
выбор, тогда всё как прежде.

**2. Поделил — полная проверка обязана быть перед слиянием.** Гейт
доказывает, что код собирается и чист, но уже не доказывает, что тесты
зелёные. Доклад «готово» при упавшем тесте ловит проверка перед
слиянием. Это та же команда без `MUAGBA_GATE_EVENT`, запущенная CI на
PR. Без неё упавший тест попадёт в основную ветку, и узнают о нём
последним.

**3. Проба `check.split` (Э6)** мерит это свойство:

- проект поделил гейт, то есть `check.sh` читает `MUAGBA_GATE_EVENT` вне
  комментариев;
- значит, CI вызывает `check.sh` на `pull_request`;
- и сам `MUAGBA_GATE_EVENT` не задаёт, иначе в CI пошла бы быстрая часть.

Что слияние идёт только по зелёному CI, держит защита ветки — проба
`git.protected`, человеческая: хостинг машине без сети не виден.

**4. Параллельные прогоны в одном дереве не пишут общих файлов.** Файл
покрытия, тестовая база с именем из пути дерева — оба случая у narta
дали красную проверку при зелёных тестах. Это правило каркаса
`check.sh`, а не код плагина: у каждого инструмента свои настройки.

## Последствия

- Каркас `check.sh` получает развилку «быстро для гейта — полностью
  иначе». Быстрая часть — проверка рамок и цель `check-quick`, если
  проект её завёл. Нет цели — гейт гоняет полную проверку, как раньше.
- Вопрос В6.9 и проба `check.split` — гейт, выпуск `0.19.0`. Проект,
  который не делит гейт, зелёный без изменений. Поделивший без CI на PR —
  красный.
- Правило исполнителя из `0.18.3` («полную проверку при сдаче делает
  гейт») при поделённом гейте значит «быструю». Полную проверяет CI на
  PR, и ревьюер видит её результат там.

## Что отвергнуто

- **Режим «быстрый гейт» в плагине** — список быстрых шагов знает только
  проект. Плагин передаёт событие, проект решает.
- **Pytest по затронутым модулям в гейте.** Определять затронутое —
  задача инструмента тестов, а не базы. Проект может сделать это в своей
  быстрой части.
