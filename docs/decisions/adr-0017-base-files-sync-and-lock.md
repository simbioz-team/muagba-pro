# ADR-0017. Файлы базы обновляются сами и заперты сторожем по последствиям

- **Дата:** 2026-10-03
- **Статус:** принято

## Контекст

Каркас копируется в проект один раз. Всё, что база потом в нём меняла, до
проектов не доезжало. Лаунчер ночи, правила агента в `AGENTS.md`,
`check-frames.py` человек переносил руками, а narta жила на версиях,
которые база давно исправила.

Требования владельца:
1. При обновлении плагина файлы проекта обновляются сами.
2. Применяет база при старте сессии.
3. Правила базы в `AGENTS.md` — управляемым блоком.
4. Один алгоритм для любого обновления, как во всех плагинах владельца:
   снять блокировку файлов каркаса → применить обновление → вернуть
   блокировку.

## Решение

**Что обновляется.** Только то, в чём нет ничего от проекта
(`sync/manifest.json`):
- файлы-механизмы — целиком;
- управляемые блоки — между метками `<!-- muagba:begin <id> -->` и
  `<!-- muagba:end <id> -->`.

Содержание проекта (миссия, конституция, workflow, спеки) не трогается
никогда: новое туда приходит через пробы и вопросы.

**Изменённое проектом не перезаписывается.** Файл обновляется, только
если его содержимое совпадает с одной из выпущенных версий
(`sync/history.json`, собирается из истории `template/`) или с тем, что
база записала в прошлый раз (`.claude/muagba-sync.json` → `written`).
Иначе — конфликт: сообщение называет файл и путь к новой версии.

**Блокировка — сторож по последствиям, а не права файловой системы.**
После каждого действия агента (`PostToolUse` на Edit, Write, Bash) сторож
сверяет файлы базы с законным состоянием (`written`) и возвращает
изменённое из копии в плагине. Агенту говорится, что откатано и почему.

Почему не `chmod a-w`:
- агент снимет его той же командой оболочки;
- git права на запись не хранит — в клоне и рабочем дереве их нет;
- людям он мешает так же, как агенту.

Почему не только запрет до действия (`protect-paths`, `guard-bash`):
они видят буквальный путь в команде. Путь в переменной или скрипт,
пишущий файл, проходят мимо — так мы сами правили защищённый лаунчер
2 октября. Сторож по последствиям смотрит на результат, ему всё равно,
каким путём пришла правка. Запрет до действия остаётся: он объясняет
отказ раньше, чем работа сделана.

**Алгоритм владельца — единственный законный путь правки:**
1. снять блокировку — открыть окно; сторож окно пропускает;
2. применить — обновление плагина или правка человека;
3. вернуть блокировку — закрыть окно и записать новое законное
   состояние.

Обновление плагина (`template_sync.py`) проходит окно само. Окно
закрывается при любом выходе, в том числе по сбою и тайм-ауту хука; окно
процесса, убитого `kill -9`, сторож считает закрытым.

Человек открывает окно командами `frame_lock.py unlock` и `lock` через
`!` в сессии. Агенту `unlock` запрещает `guard-bash`. Изменённое
человеком в окне закрепляется за проектом (`held`): база его больше не
сторожит и не перезаписывает, а о новой версии сообщает. Скопировал
новую версию на место — файл снова базы.

Учёт (`.claude/muagba-sync.json`) в списке защиты каркаса. Окно лежит в
`.git` — это состояние checkout'а, а не факт о проекте.

## Пределы

- Сторож срабатывает после действия: между правкой и откатом агент
  может прочитать или исполнить изменённый файл в той же команде.
- Агент, правящий учёт или окно через путь в переменной, сторожа
  обманет. Это порог с отметкой в журнале (`guard hook=frame-lock`), а
  не стена.
- Сторожится только то, что база записала из текущей версии. Конфликт и
  закреплённое за проектом — решение человека, не сторожа.

## Последствия

- Выпуск базы включает шаг `template_sync.py --build`: `sync/` собирается
  из `template/`. `run.sh` проверяет, что сборка не отстала.
- Проекты получают блок правил в `AGENTS.md` автоматически. Если правила
  уже были в файле вне блока, сообщение просит убрать повтор.
- Обновлённые файлы — изменения в рабочем дереве проекта. Сообщение
  просит закоммитить их отдельным коммитом.
