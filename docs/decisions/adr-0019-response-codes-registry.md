# ADR-0019. Коды ответа сетевых взаимодействий — по стандарту и из реестра

- **Дата:** 2026-10-23
- **Статус:** принято

## Контекст

Владелец 23.10.2026 поставил три требования ко всем проектам:

1. любое сетевое взаимодействие в коде отвечает кодами по стандарту;
2. добавить код можно только явно, убедившись, что он действительно нужен;
3. код однозначно идентифицирует событие.

Основание — исследование Nastavnik (`docs/research/standart-kodov-otveta-api.md`
в его репозитории): около 240 кодов событий без реестра; шесть синонимов
ошибки ввода; один код на паузу и прекращённый урок, которые фронт различает
регуляркой по русскому тексту; текст исключения в ответе 500. Готового
стандарта «код → событие» нет ни у кого. У Google (AIP-193), Azure, Stripe,
GitHub и Zalando схема одна: статус транспорта — класс исхода, отдельный
идентификатор — точное событие, каталог идентификаторов — часть контракта,
соблюдение держится на машине.

Это правило о том, как строить, а такие по ADR-0009 базе чужие. Исключение
принято владельцем явно; дополнение — в ADR-0009.

## Решение

**Принципы — в базе, для любого стека и транспорта.**

1. **Два уровня.** Класс исхода — по стандарту транспорта: HTTP — RFC 9110,
   тело ошибки — RFC 9457 (`type`); gRPC — канонические коды и `reason`;
   очередь или событие — поле типа. Событие называет идентификатор из
   реестра. Одно событие — один код, один код — одно событие, у кода один
   класс.
2. **Клиент переживает незнакомый код** — ведёт себя по классу. Иначе
   добавление кода ломает клиента, и требование 2 теряет смысл. Ветвиться
   по тексту сообщения нельзя.
3. **Реестр — JSON-файл, по одному на сервис.** Код получает перечисление
   генерацией из него, а не наоборот: тогда одна проверка базы читает реестр
   любого стека. Поля: `id`, `class`, `meaning`, `client_action`, `state`
   (`active` | `deprecated` | `unreviewed`), `added_by`; у выведенных —
   `replaced_by`, `remove_after`; `name` — имя элемента перечисления.
   `id` уникален по всем реестрам репозитория; разным сервисам нужен
   префикс (`/problems/<сервис>/<slug>`). Ошибку зависимости сервис
   переводит в свой код, а не пробрасывает.
4. **Добавление — явное**, записью с `added_by` и ответом «почему не подходит
   существующий». **Изменение — только выведением:** новый код, старый —
   `deprecated` с заменой и сроком, удаление после срока.
5. **Контроль — `.claude/check-codes.py`** (файл базы, синхронизируется,
   без конфига ничего не делает), вызывается из `check.sh`:
   - соблюдение: в коде нет кода вне реестра (по объявленным шаблонам
     употребления — литерал, ссылка на перечисление; их может быть
     несколько), запись полна, `id` и `name` уникальны;
   - актуальность: нет `active` без употребления; выведенный с истёкшим
     сроком не употребляется;
   - контракт: против реестра на базе ветки — запись не исчезла и не
     сменила класс, кроме выведенной после срока; новая — с `added_by`.
6. **Храповик.** `unreviewed` — только для кодов, внесённых при заведении
   реестра (`check-codes.py adopt`). Старое разбирается по задачам, новое —
   сразу по правилам; зелёный проект от заведения реестра не краснеет.
7. **Проба `check.codes` (Э6)** мерит свойство: решение записано
   (`none` с причиной или реестры), проверка вызывается из `check.sh`, и
   каждый шаблон находит хоть одно употребление — иначе проверка зелёная,
   потому что смотрит мимо кода. Вопрос — В6.10.
8. **Роли.** Исполнитель берёт код из реестра, новый обосновывает в
   коммите; ревьюер считает находкой новую запись без обоснования,
   удаление вместо выведения и ветвление по тексту.

**Что базе не принадлежит.** Формат тела и обработчики ошибок фреймворка,
список разрешённых статусов, OpenAPI из реестра, линтеры схемы, контрактные
тесты по стенду, линтер фронта на ветвление по тексту — проект, по его
стеку. Nastavnik делает это в своём ADR-113.

## Последствия

**Проще:** код события нельзя завести молча, а сломать контракт —
незаметно; реестр не зарастает мёртвым.

**Сложнее:** проекту с сетевыми ответами нужен реестр и разбор старых
кодов. Проба Э6 краснеет у каждого проекта, пока он не ответит на В6.10 —
поэтому выпуск минорный (0.22.0).

**Теперь нельзя:** проверять в базе формат тела или стек-специфичные
правила. Всё, что база знает о кодах, — реестр в JSON и шаблоны
употребления.

## Отвергнуто

**Реестр — модуль кода (enum).** Проверка базы стала бы своей под каждый
язык. Перечисление генерируется из JSON и сверяется проектом на свежесть.

**Плоская уникальность без префиксов.** Общие `validation-error` и
`not-found` есть у каждого сервиса; называть их искусственно хуже, чем
дать префикс сервиса.

**Гейт, краснеющий на всех существующих кодах сразу.** Проект с сотней
кодов покраснел бы целиком и отключил бы проверку. Храповик `unreviewed`.

**Только договорённость.** Именно так возник беспорядок в Nastavnik.
