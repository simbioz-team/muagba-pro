# ADR-0010. Конвейер разработки фич — чужой, наше дело интерфейс к нему

- **Дата:** 2026-09-21
- **Статус:** принято

## Контекст

База несла скил `new-feature`: интервью, `spec.md`, `plan.md`, `tasks.md`,
сверка с конституцией, разметка параллельных задач. То есть `/speckit-specify`,
`/speckit-plan` и `/speckit-tasks`, написанные заново.

Сверка с первоисточником оказалась не в нашу пользу. В шаблоне спеки Spec Kit
есть то, чего у нас не было: приоритизированные пользовательские истории с
требованием независимой тестируемости, сценарии в форме `Given / When / Then`,
где исход обязателен, технологически нейтральные измеримые критерии успеха,
краевые случаи, чеклист качества с итерациями. Команда `/speckit-clarify`
ведёт интервью по таксономии покрытия из девяти категорий. `/speckit-analyze`
находит дубликаты требований, неоднозначность, дрейф терминологии и **пробелы
покрытия «требование → задача»** — то есть перекрывает нашу проверку формы
целиком. Лицензия MIT, развивается, есть расширения и процесс приёма от
сообщества.

Контрольный факт: проект, который вёл на базе живую разработку, `new-feature`
**ни разу не запустил** — скил `disable-model-invocation`, а человека в цикле
не было. Спеки написали по его тексту и получили 2.7 из 5 по продуктовому
качеству. Из шести системных пробелов, найденных в них, **четыре закрывает
чужой шаблон одним своим наличием**.

Даже контракт `[P]` со списком файлов, который мы считали своим вкладом в
параллельную работу, оказался дословным форматом Spec Kit — и у них богаче:
есть метка истории и явные зависимости между задачами.

## Решение

**База конвейер разработки фич не несёт.** Его выбирает проект: Spec Kit,
OpenSpec, BMAD, своя форма.

**База объявляет интерфейс к выбранному.** Проект записывает в
`specs/README.md`, раздел «Конвейер фич», пять полей:

| Поле | Зачем |
|---|---|
| **Артефакты** | где лежат файлы фичи и как зовётся файл спеки |
| **Готова к коду** | по какому признаку видно, что спеку можно брать в работу |
| **Задача → требование** | как задача ссылается на требование |
| **Готовность ставит** | кто и когда переводит спеку в готовую |
| **Проверка формы** | чем форма проверяется машинно и откуда вызывается |

Форму предложил тот самый проект, и она лучше первоначальной идеи «записать
имя конвейера в `docs/toolchain.md`»: по имени гейту читать нечего. С полями
хук «нет кода без спеки» и проверка покрытия становятся возможны **при любом
выборе**.

Поле «Готовность ставит» — не формальность. Оно единственное, что стоит между
проектом и повторением 2.7: если готовность ставит агент, это записано, и
видно, чем платим.

**Форма базы остаётся вариантом по умолчанию** — проект, не взявший чужой
конвейер, не должен остаться ни с чем. В неё дописано то, без чего она давала
2.7: сценарии, доходящие до исхода; продуктовые измеримые критерии приёмки;
сверка с замыслом таблицей по образцу сверки с конституцией; «вне рамок» в
двух частях — «никогда, потому что» и «не в этой фиче». Скрипт
`scripts/check_specs.py` остаётся её доступной реализацией: он проигрывает
`/speckit-analyze` по составу проверок, но он **скрипт, а не промпт** — код
возврата и место в CI.

### Что при этом остаётся нашим

Разбор четырёх команд Spec Kit нашёл ровно две вещи, которых у него нет.

1. **Сверка с продуктовым замыслом проекта.** Ни `/speckit-specify`, ни
   `/plan`, ни `/tasks`, ни `/constitution` её не делают: сверяются только с
   конституцией. Замысел, не попавший в спеку, не попадёт и в код.
2. **Координация параллельных исполнителей.** Ни одного упоминания `worktree`,
   `claim`, `lock` или `assign` в обеих командах и обоих шаблонах.
   Параллелизм расписан подробно, но раздача выглядит как «Developer A:
   User Story 1» — то есть люди, договаривающиеся вне репозитория. Механизма,
   которым **агент захватывает задачу**, нет (`ADR-0008`).

Плюс память проекта о стеке и раскладке: команда плана читает только спеку и
конституцию, а девять полей технического контекста и выбор раскладки заполняет
**на каждую фичу заново**. У нас это решается один раз на Э4.

## Альтернативы

**Требовать Spec Kit как класс А.** Отклонено. Он Python-CLI со своей
установкой, а не плагин Claude Code. Главное свойство базы — ставиться на любой
проект без подготовки (`ADR-0002`, `ADR-0007`), и требование чужой установки
его ломает.

**Держать свой конвейер и догонять.** Отклонено, см. `ADR-0009`.

**Ничего не проверять: конвейер — дело проекта.** Отклонено. Форма, которую
ничего не проверяет, не держится даже у того, кто её придумал: в проекте,
заведшем такую проверку, она сразу нашла 23 расхождения в спеках, написанных
часом раньше.

**Проверять форму нашим скриптом безусловно.** Это и была `0.11.0`.
Откачена — см. `ADR-0011`.

## Последствия

**Проще:** база перестала конкурировать с тем, что развивают сотни людей, и
занялась тем, чего не делает никто.

**Сложнее:** пять полей надо заполнить, и заполняет их человек. Пустой
конвейер теперь роняет Э9.

**Плата, которую надо назвать честно:** проба фиксирует **выбор**, а не
принуждает. Проект вправе записать «проверки формы нет», и гейт это пропустит.
Заставлять — значит навязывать свою форму, из-за чего и откатывали `0.11.0`.
Три прогона обкатки показали цену сразу: все три изобрели **три разные формы**,
ни одна не проверяется машинно, и ни у одной нет явной связи «задача →
требование». Теперь это хотя бы записано в их документах открытым текстом.

**Теперь нельзя:** добавлять в базу проверку, которая знает форму артефактов
фичи. Всё, что база знает о конвейере, — пять объявленных полей.
