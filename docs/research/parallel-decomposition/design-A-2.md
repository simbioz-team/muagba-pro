# Команда A, круг 2: контракт и срезы, плюс стек по контракту

Дата 2026-11-24. Опирается на `design-A-1.md`, `design-B-1.md`,
`research.md`. Новые проверки этого круга лежат рядом:
- `sim/check_b_edges.py` прогоняет модель B (`simB/sim.py`) с одной правкой,
  которую требуют её же правила;
- `sim/sim_a2.py` — событийная модель со стеком по контрактному ребру,
  честным каскадом и приёмочными тестами отдельными задачами;
- `sim/k_depth.py` сравнивает глубину волны 0: 1 против 2.

Везде 300 прогонов. Длительности: исполнитель 10 мин (deep ×1.6), ревью 8,
доработка 7, вливание 2, rebase 3, разброс 0.7–1.4.

## Спор

### Где мы с B совпадаем, хотя B пишет, что спорит

B заявляет: «Не уступлю: „достаточно нарезать срезами“. Срез не видит общей
сущности» (B §11). Такой позиции у A нет. В A-1 общие сущности, меры,
миграции и порты собраны в `contracts.md`, и у каждой один владелец — задача
К (A-1 §2, шаг 1). У `[V]` нет полей `Сущность:`, `Мера:`, `Миграция:` по
определению (A-1 §3). Пересечения `Файлы:` проверяет проба плана (A-1 §5).
Это и есть «карта владения» B, только под другим именем. Спорить по этому
пункту не о чем: обе команды пришли к одному и тому же механизму. Различия
в другом, и они разобраны ниже.

### 1. Где B неправ

**1.1. «План ~1.75×, конвейер ~2×, причины независимы, выигрыши
умножаются» (B §8).** Расчёт противоречит правилам самого B. На послойном
графе модель B даёт конвейеру 354 → 157 только потому, что преемник
стартует от сданного коммита по **любому** ребру, в том числе по ребру
общей сущности `S{s-1}model → S{s}model`. Правило B §4 велит по рёбрам
«поведение» и «данные» стартовать от влитого. Я прогнал модель B без
изменений, кроме одного: для этих рёбер преемник ждёт вливания
(`sim/check_b_edges.py`).

| Граф B | serial | pipe как у B (стек везде) | pipe по правилам B (слот свободен, преемник ждёт вливания) |
|---|---|---|---|
| послойный, 30 задач | 353 | 157 | **353** |
| плановый, 24 задачи | 202 | 105 | 177 |

Без стека освобождение слота на лестнице не даёт ничего. Это тот же вывод,
что в A-1 §7 (345 = 345). Значит, выигрыши не независимы, а **условны**:
конвейер работает только на широком графе или там, где есть законный стек.
Довод «умножаются» снят, и с ним снят тезис B, что можно получить ~2× на
текущих послойных планах наставника одним конвейером. Для владельца отсюда
главное: **без перестройки плана ускорения не будет**, какой бы ни была
организация ревью.

**1.2. Срез, разрезанный на «сервер ∥ клиент → сценарий» (B §5.4 и граф
`planned`).** Задача «сценарий» ждёт **работающих** сервера и клиента, то
есть по классификации B это ребро «поведение». А B §5.5 называет такое
ребро «красным флагом». В модели B оно при этом стекуется, как контрактное.
Шесть таких рёбер на фичу — шесть мест, где доработка сервера после ревью
(42–44% отказов) ломает уже сделанный «сценарий». Склейку сторон делают
приёмочные тесты, написанные против контракта (см. 2.2). Отдельная задача
склейки не нужна. Если срез больше S, его режут по сторонам против
контракта (сервер ∥ клиент), но **без задачи склейки**. Это я принимаю из
B, а склейку нет.

**1.3. Вторая LLM-линза «тесты и соседи» на Sonnet (B §7.3).** Обе её части
механические:
- «соседи» — это `git merge-tree` с ветками в полёте, то есть
  `task_pairs.py merge` на N веток. Скрипт отвечает за секунды и не
  ошибается. Запуск агента ради вызова скрипта — это холодный старт
  (кэш живёт 5 минут), ~38 запросов и ~$0.5–0.9 на задачу без новой
  информации;
- «тест ничего не держит» ловит проверка удержания из A-1 §7.2 (тесты
  `Готово-когда:` краснеют при откате кода среза). Её вывод прикладывается
  к сдаче.

Из 19 отказов при 4 исполнителях 16 — пересечение с соседом. Их снимает
план, остаток ловит `merge`. Для второго ревьюера работы не остаётся.
Ревьюер один, с узкой линзой: логика и `Готово-когда:`/`AC-n`.

**1.4. Порог критического пути `L ≤ ⌈N/K⌉ + 2` (B §6).** По оценке Грэма
для списочного расписания T ≤ W/K + L
([list scheduling](https://en.wikipedia.org/wiki/List_scheduling),
[Brent](https://en.wikipedia.org/wiki/Analysis_of_parallel_algorithms#Execution_on_a_limited_number_of_processors)).
Порог B допускает L ≈ W/K, а значит, в худшем случае T ≈ 2W/K: половина
слотов простаивает. Это сегодняшние 2.1–2.4 из 4, только узаконенные.
Беру формулу B как **страховку** для фич вида `[S]`, но главная мера —
занятость по смоделированному расписанию (она есть у обеих команд). И
целевой путь — К → V → Х, то есть **L ≤ max(4, ⌈W/(2K)⌉)**. Такой порог
гарантирует занятость не ниже 2/3 даже по худшей оценке.

**1.5. Волна 0 глубиной 2 (`C1 ∥ C2 → C3`, B §5.3).** `sim/k_depth.py`:
глубина 2 добавляет +13 мин при p = 0.3 и +14 мин при p = 0.15, то есть
~9% времени фичи. Что делает C3 у B: генерирует клиент и фикстуры. Это
**выход** той задачи К, которая владеет схемой, а не отдельное звено.
Остаюсь при глубине 1. Цепочка К → К допускается, только если её нельзя
сложить в одну задачу, и с полем `Почему не одна:`.

**1.6. Приёмочные тесты как задачи волны 0 перед срезами (B §7.1).** Если
срезы ждут свои тесты (8 задач тестов после К), фича идёт 211 мин против
183 без таких задач (`sim/sim_a2.py`, п. 3): **+15%** на блокирующей фазе.
Сама идея B верна (2.2), место выбрано неверно.

### 2. Где B прав, и я уступаю

**2.1. Стек по контрактному ребру. Уступаю.** В A-1 срезы стартовали от
**влитого** К, и ревью контракта (самое долгое, Opus) стояло на критическом
пути целиком. У B довод с источником: Google, автор продолжает стеком
поверх сданного CL
([small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)).
Я проверил его на своей модели с каскадом, который **хуже** честного:
если ревью К говорит «нельзя сливать», каскад задевает все уже открытые
срезы, даже ещё не взятые (`sim/sim_a2.py`, п. 2):

| К1 ∥ К2 + 22 среза + хвост, N = 4, p = 0.3 | мин | занято |
|---|---|---|
| без стека (A-1) | 183 | 1.99 |
| стек, каскад q = 0 (только rebase) | 155 | 2.32 |
| стек, q = 0.3 (треть отказов К меняет смысл шва) | 158 | 2.55 |
| стек, q = 0.6 | 164 | 2.67 |
| p = 0.45 для всех задач: без стека / стек q = 0.3 | 232 / 202 | |

Выигрыш −10…−15% держится даже при q = 0.6. Довод убедительный: источник
плюс расчёт с наказанием на моей стороне.

Условия, которые я добавляю к стеку:
- стек только по ребру «контракт»;
- срез, начатый от сданного К, не вливается раньше К (так и в модели);
- если ревью К вернуло **смысл** шва (тип, обязательность, код ответа), а не
  мелочь, это ломающая поправка из A-1 §6. Потребители шва останавливаются
  одним сообщением, а не тихим rebase;
- ревьюеру К называется, что срезы уже идут поверх. Отказ от этого не
  смягчается: дешевле переделать четыре среза, чем двадцать два.

**2.2. Независимые приёмочные тесты. Уступаю частично.** Довод B: тест,
который пишет тот же исполнитель, что и код, подгоняется под код, а это и
есть отказ «правит тест вместо кода» из рамок базы. Проверка удержания из
A-1 ловит пустой тест, но не тест, который проверяет не то, что требует
`AC-n`. Независимость автора закрывает именно этот случай. Довод
убедительный, потому что B связал его с конкретной причиной отказа и с
ролью `acceptance`, которая править не может.

Но место другое (см. 1.6). Задачи `[T]` пишутся **по `contracts.md` и
`AC-n` параллельно с К**, по одной на историю, а не на срез. Они занимают
слоты, которые в фазе К всё равно простаивают (К = 2 задачи при N = 4).
Срез может **начаться** без них, но **влиться** только после них. Цена:
+5 мин (188 против 183), занятость 1.99 → 2.24. Механизм метки берём у B:
strict xfail / `test.fails`. Тогда `check.sh` зелёный на влитых тестах до
кода, а снятая метка доказывает переход «красный → зелёный». Проверка
удержания остаётся для юнит-тестов среза.

**2.3. `next --slots K` с рангом критического пути (HLFET). Уступаю.** В
A-1 не было правила, **в каком порядке** брать готовые задачи. При ширине
22 это неважно, а у хвоста фичи и у доработок важно. Доработка получает
ранг своей задачи (B §7.6). Это классика списочного расписания, а не
изобретение.

**2.4. Расширить `task_pairs.py`, а не заводить `plan_width.py`.
Уступаю.** Разбор `tasks.md` уже живёт в `task_pairs.py`. Второй скрипт с
тем же разбором — новая сущность в базе без новой функции.

**2.5. Мелкое, но верное.** Предупреждение «deep на критическом пути»
(Opus идёт 11–17 мин против 7–10). Размер S ≤ ~150 строк, M ≤ ~300. Статус
`сдана` в трекере Narta отдельно от `в работе`: слот считается по
`в работе`. Если приёмочный тест неверен, исполнитель останавливается с
докладом и сам тест не правит.

### 3. Где остаюсь при своём без уступки

- **Поля.** Оставляем `Файлы:` и `Контракт:`. `Владеет:` и `Читает:` у B —
  те же поля под новыми именами, и `task_pairs.py` уже читает `Файлы:`.
  Синонимы в формате — это вторая форма записи, которую придётся
  поддерживать вечно.
- **Доля волны 0 по оценке времени, а не по числу задач.** У B «≤ 15%
  задач», но одна deep-задача К весит как 1.6 обычных. Меряется то, что
  блокирует, то есть время.
- **Пятый исполнитель окупается только на широких фичах.** У обеих
  команд N = 5 против 4 даёт −5…−9% (B: 105 → 94; A-2: 134 → 122). Падение
  доли доработок с 0.3 до 0.15 даёт больше (158 → 134). Порядок вложений:
  сначала форма плана, потом качество сдачи, потом N.

### 4. Что открыто для круга 3 (проверяется на baseline-фичах)

- q — доля отказов К, меняющих смысл шва. При q > 0.6 пересмотреть стек.
  Это совпадает с критерием уступки B (каскад > 20%).
- Хватит ли Sonnet для задач `[T]` или нужен Opus.
- Пул ревьюеров R: в моделях R = N. Если у наставника R ограничен двумя,
  посчитать заново.

### Форма задачи

```markdown
- [ ] T014 [V] История 2: экспорт банка заданий в CSV
  Срез: US2/сценарий «учитель выгружает банк»
  Контракт: C1 (GET /api/banks/{id}/export, ExportRow), C2 (порт BankReader)
  Файлы: apps/banks/export/views.py, apps/banks/export/csv.py, web/src/banks/ExportButton.tsx, tests/banks/test_export.py
  Зависит от: C1 (контракт), C2 (контракт)
  Приёмка: AC-4, AC-5 (tests/acceptance/us2/, из T005)
  Готово-когда: test_export_roundtrip, test_export_empty_bank — зелёные, без кода среза краснеют; xfail в tests/acceptance/us2 сняты
  Риск: обычный
  Размер: S
```

Виды задач: `[K]` контракт, `[T]` приёмочные тесты истории, `[V]` срез,
`[H]` хвост, `[S]` последовательная (с полем `Почему не срез:`).

Новые поля по сравнению с текущей базой: вид в скобках, `Контракт:`,
`Приёмка:`, `Готово-когда:`, `Риск:`, `Размер:` и тип ребра в
`Зависит от:`. Поля `Файлы:`, `Сущность:` и `Мера:` уже читает
`task_pairs.py`.

### Рёбра

| Тип | Когда преемник стартует | Когда вливается | Ограничение |
|---|---|---|---|
| `контракт` | от **сданного** коммита предка | после вливания предка | норма для К → V и К → T |
| `поведение` | от **влитого** | после | только с `Почему не по контракту:`. Между срезами — красное в пробе |
| `данные` | от **влитого** | после | миграции и фикстуры живут в К, поэтому вне К такое ребро — красное |
| `ресурс` | не одновременно | — | `serial` из `pair-rules.txt` |

Без типа ребро считается `поведением`. Внутри истории слоёв нет. Большой
срез режется по сторонам против контракта (сервер ∥ клиент), а задачи
склейки нет: склейку держат тесты `[T]`.

### Проба плана (`task_pairs.py plan`, отчёт, не гейт)

| Мера | Порог |
|---|---|
| Занятость по списочному расписанию HLFET в веере | ≥ 0.8·N |
| Критический путь в весах (deep = 1.6) | ≤ max(4, ⌈W/(2K)⌉); страховка для `[S]`-фич — ⌈W/K⌉ + 2 |
| Время волны 0 | ≤ 20% оценки фичи; глубина 1 (К → К только с `Почему не одна:`) |
| Пересечение `Файлы:` у задач без пути между ними | 0, кроме `shared` |
| `[V]` с `Сущность:` / `Мера:` / `Миграция:` | 0 |
| Шов в `contracts.md` без владельца или без потребителя | 0 |
| `AC-n` → `[T]` → `[V]` | покрыто на 100% |
| Ребро «поведение» или «данные» между `[V]` | 0 или обоснование |
| deep или M на критическом пути | предупреждение |

Отчёт считается для N = 3, 4, 5, и в нём видно, с какого N расширять
бесполезно.

### Поправка контракта посреди веера

Как в A-1 §6: исполнитель докладывает, а не правит. `K-amend` — только
добавление, с высшим рангом. Потребителям шва уходит одно сообщение
«rebase». Ломающая поправка останавливает потребителей и записывается в
журнал как ошибка плана. Новое в A-2: отказ ревью К по смыслу шва при уже
идущем веере обрабатывается так же.

### Трекер Narta

Статусы: `готова` → `в работе` → `сдана` → `на ревью` →
(`доработка` → `сдана`) → `влита` → `принята`. Слот исполнителя считается
по `в работе`.
