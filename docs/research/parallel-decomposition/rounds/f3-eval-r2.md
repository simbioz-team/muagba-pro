## 4. Общее для обоих

### 4.1. Существенное: генерируемые файлы и слияние

Хуки проекта с `--check` пишут как минимум шесть файлов:
- `module-graph.json`, `module-map.md`;
- `api-problems.json`;
- `docs/TAGS.md` (`check_docs_index.py --fill`);
- `tech-stack.md`;
- `process-map.json` и `development-process.md`.

Каждый меняет почти любая серверная или документная задача. Если `task_pairs.py merge`
сливает их как текст, при 4 исполнителях получится 5–10 механических «конфликт → доработка»
на фичу, и часть из них на пути. Шаг 9 `design.md` назначает такой доработке ревью не нужно,
но запуск исполнителя она стоит.

Поправка базы, не плана: в `pair-rules.txt` класс `shared-generated` с командой перегенерации.
`task_pairs.py merge` при конфликте только в таких файлах берёт любую сторону и запускает
генератор, а не отдаёт задачу в доработку. Список файлов для проекта выводится из хуков вида
`gen_* --check` / `--fill` в `.pre-commit-config.yaml`. Это один раз за проект и годится для
любого стека. `design.md` §9 п. «hold при правке shared» это уже предчувствует.

### 4.2. Существенное: CI партиями не работает при `cancel-in-progress`

В `cicd.yml` стоит `concurrency: group: cicd-${{ github.ref }}`, `cancel-in-progress: true`.
Каждый пуш в ветку фичи отменяет идущую проверку той же ветки. Партии у A приходят на 51-й,
74-й, 106-й, 117-й и 143-й минуте, у B — похоже. Промежутки 11–32 мин, проверка идёт 15–28 мин.
Значит, часть партий не проверяется вовсе, а красный результат покрывает несколько партий
сразу. «Красная партия — пополам» (`design.md` п. 1.10) тогда требует отдельных прогонов по
15–28 мин на общих трёх раннерах.

Что сделать (в процесс, координатору):
- пушить партию, только когда прошлая проверка закончилась, — по сути одна партия на 20–30
  мин;
- либо гонять каждую партию на своей ссылке `ci/<фича>-<n>`. Раннеры общие, поэтому это
  очередь, а не параллель.

В расписании CI — последовательный ресурс. Он добавляет ~10–20 мин на путь, если последняя
партия ждёт предпоследнюю.

### 4.3. Среднее: стык «вторая сторона» в карточке проверяется только на стенде

Сервер ручки карточки (A T018–T020, B T012) и клиент (A T021–T023, B T013/T014) видят друг
друга только через типы C12/C13 и через `[T]` каждой стороны отдельно. Первая общая проверка —
приёмка на `trn`. В бейзлайне именно этот стык (409, «Отмена» по последнему чтению, правка
списка) дал 4 круга.

Дешёвое лекарство без нового инструмента: в К завести **примеры тел ответа** — GET 200, POST
201, 409 с `current_state`, 422, 403 — одним JSON-файлом шва. Серверный тест сверяет с ним
форму ответа, клиентский node-тест кормит им редьюсер. Тогда расхождение сторон ловится в
`check.sh` любой из сторон. B уже держит `data-testid` в `contracts.md`, это та же мысль.

### 4.4. Среднее: `effective_steps` никто не называет

`exam_solver/services.py:259` (`_candidate_views`: список расхождений очереди и `candidates()`)
читает шаги через `step_edits.effective_steps` из старой таблицы правок. На ветке эту функцию
переписали внутри `step_edits.py`, фасад не трогали. В обоих планах владелец партии (A T014,
B T010) говорит о `read_steps` и `edit_step`, а об `effective_steps` молчит. Нужно дописать
пункт в `Готово-когда:`: «правка шага видна в `discrepancies()` и в полезной нагрузке эталона
очереди», с тестом.
