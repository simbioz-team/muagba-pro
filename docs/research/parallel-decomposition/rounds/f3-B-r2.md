Почему C7 и C9 — заглушки с ленивым импортом: тогда T003 не зависит от кода T005–T016, а срезы
стартуют от влитого К, не от сданного. Если проверки проекта не пропустят ленивый импорт ещё не
существующего модуля, это поймает пробное слияние К-партии. Запасной вариант — в заглушках
поднимать `NotImplementedError` без импорта.

- Сегодняшний режим на том же графе (`block_r2.py`: слот держится до вливания, тесты пишет
  исполнитель, +40% к весу среза): 206 / 271 / 318 до `[H]`.

## 7. Тесты, документы, ревью, вливания

- **Тесты.** Приёмочные лежат в `[T]`, каждый в своём файле. Тест среза — в файле среза. Общие
  фикстуры — в К: C2 (T001), C4 (T002), C17 (T003). `test_steps.py` правит только T010. Имена
  модулей подобраны под `GROUP_RULES` (§1); новая строка пробы ловит модуль, который попал в `core`.
  Staff — `node --test` по `*.test.cjs`, раннер и шаг CI ставит T004.
- **Документы.** Каждая ручка — свой файл в `docs/api/endpoints/`: заводит К (T003), примеры
  дописывает срез. Раннбук 0296 — свой файл T008. Строки реестров, которые проверяет гейт
  (`docs/api/README.md`, публичные имена в `exam_solver/README.md`), пишет T003; остальное — T028.
  `api-problems.json` и `module-graph.json` генерируются: при rebase их перегенерируют, а не сливают
  (строка `shared-generated` в `pair-rules.txt`).
- **Ревью.** Пул R = 3, ревьюер берёт сданное по рангу пути. Линзы:
  - C0 — без LLM: скрипт сверяет текст с контрактом;
  - T001–T004 — «хватит ли срезам и курсу»;
  - `[T]` — «каждый AC покрыт, тест бьёт обе стороны»;
  - срезы — логика, `Контракт:`, `Готово-когда:`;
  - T016 — «каждый случай v6 §2.13 и обратный случай».

  Механику (`check.sh`, пробное слияние, `hold`) делает скрипт при сдаче.
- **Опыт: ревью по ходу на звеньях пути** (T002, T005, T006, T007, T010, T012). Ревьюер читает
  коммиты, пока задача идёт; после сдачи он смотрит дельту (~3 мин вместо 8). В базовый план это
  **не входит**. По модели при K = 4: до `[H]` 215 → 193 (p = 0.3), 244 → 215 (p = 0.43), цена —
  +6 запусков ревью (~$9). В модели p на этих звеньях снижен ×0.7, и это **не измерено**. Без этого
  снижения выигрыш — только задержка ревью, около −8%. Замер: координатор пишет p для звеньев с
  ревью по ходу и для остальных deep M. Если разница меньше 0.1 на двух фичах, опыт закрывается.
- **Вливания.** Срез вливается после своих К, своих `[T]` и задач из `Вливание: после`. Партии:
  - обязательная — **{T008, T010, T011}**;
  - К — {T001, T002, T003, T004} (пробное слияние проверяет `apps.py`);
  - далее по 3–4: {T005, T006, T007}, {T009, T016, T013, T014}, {T012, T015}, {T028}.

  CI идёт по партиям. На пути только последняя партия и полный прогон.
- **Внешнее.** Ветка — от вершины `feature/course-pipeline-concept`. Вопрос по v6 §2.13 соседней
  сессии уходит на шаге 1. Вливание в ветку пайплайна делает чужая сессия: это ожидание вне нашего
  расписания.

## 8. Разбор: конфликты, простой, что не получилось

### 8.1. Отступления от `design.md`, названные

1. **Четыре задачи К вместо 1–3.** Оценщик потребовал резать T001. Три серверные К (типы, схема,
   банк) и одна клиентская — меньшее число, при котором каждая ≤ M. Доля К — 16% ≤ 20%.
2. **Контрактный коммит.** T002 и T003 подтягивают первый коммит T001, а не влитый T001. По
   букве §4 это стек от `[K]` при 8 срезах (= 2K), то есть красное. По смыслу стек запрещён из-за q:
   отказ ревью предка по смыслу шва задевает начатых потребителей. У C0 q ≈ 0 по построению: это
   текст уже согласованного контракта, и сверяет его скрипт. Менять смысл C0 может только поправка
   контракта, а она и без стека останавливает потребителей. Поправка — §9 п. 2. Если поправку не
   примут, T002 и T003 ждут влитый T001. Тогда, по `variants.py` в режиме `r2nostack`, S = 103,
   P = 4.59, а до `[H]` +29…+35 мин (186 / 245 / 279). Это главный рычаг круга 2: он стоит
   отдельного решения по `design.md`.
3. **Слот сверх K для звена пути.** Правило даёт −4…−15 мин (`ov.py` против `f3b_r2.py`). Средняя
   занятость при этом 2.9–3.2, то есть пятый исполнитель на всю фичу не нужен.

### 8.2. Почему P ≈ 5, а не ≥ 8

Хребет `T002 → T006 → T007 → T010/T012` — четыре звена deep, ~88 веса. Проверенные варианты
(`variants.py`, K = 4, p = 0.3, до `[H]`):

| Вариант | S | P | до `[H]` |
|---|---|---|---|
| План круга 2 | 98 | 4.83 | 215 |
| Чтение внутри T002 при честном L (34) | 108 | 4.18 | 219 |
| Чтение внутри T002, если бы оно было M (24) | 98 | 4.50 | 211 (но размер > M — запрет §4) |
| T012 на GET и POST (+1 задача) | 98 | 4.91 | 213 |
| T007 без стека от T005 | 98 | 4.74 | 224 |
| Круг 1 с честным весом T001 | 108 | 3.71 | 217 |

Деление T012 даёт −2 мин ценой лишней задачи и ревью: в шуме, не берём. Вывод тот же, что в круге 1:
**фича с новым ядром даёт P ≈ K, не 2K.**

## 9. Поправки к `design.md` (предложение)

1. **§5, совет по K.** «P < K — красное, совет K = ⌊P⌋» дополнить так: если на пути есть цепочка
   `[S]` из трёх и более звеньев («фича с ядром»), K выбирается по модели или по границам Грэма для
   K и K − 1, а не по ⌊P⌋. Довод: в круге 1 при P = 3.99 K = 3 было медленнее K = 4 на 10–12%, в
   круге 2 — на 12–15%. Красное по P при этом остаётся и возвращает план `architect`.
2. **§4, контрактный коммит.** Первый коммит задачи К, который дословно переносит текст
   согласованного контракта (типы, сигнатуры) и сверяется скриптом, другие К могут подтягивать при
   появлении. Это не стек: q такого коммита ≈ 0 по построению.
3. **§3 шаг 7, звено пути не ждёт слота.** Задача с рангом, равным S (на критическом пути), стартует
   сразу, даже если K слотов заняты. На этой фиче это −4…−15 мин при средней занятости < K.
4. **§4, поле `Вливание: после … / вместе с …`.** Это условие вливания, а не старта. Без поля его
   держит только память координатора (партия {T008, T010, T011}; T009 ⇢ T010, T012).
5. **§3 шаг 7, ранг `[T]`.** Ранг задачи `[T]` равен рангу среза, вливание которого она держит, а не
   её собственному весу. Иначе `[T]` уходят в конец очереди и задерживают вливание пути.
6. **§5, новая строка пробы: «тест-модуль попадает в `core`».** Сверка имён из `Файлы:` с
   классификатором проекта (`test_registry.py`) — красное. Иначе семь задач правят один JSON.
7. **§5, новая строка пробы: «`[T]` на стороне без раннера CI».** Красное: строгий xfail, который
   никто не гоняет, не держит ничего. Раннер заводит задача К этой стороны.
8. **§2.1, ширина в точке** (из круга 1, не проверено): мерить «срезы < 2K» по срезам, которые ждут
   данное звено, а не по всей фиче. Остаётся открытым.
