писатель → писатель журнала кандидата → ручки. Это три звена `[S]`, и разрезать их по смыслу нельзя

P ≈ 4 вместо ~2.7 без задач `[T]` и `[E]`. P ≥ 2K = 8 на этой фиче недостижимо ни при какой

- **AC-1** `write_version`: при `based_on` ≠ голова — `VersionConflict`, ничего не записано.
  Правка разных шагов от одной головы: вторая получает 409.
- **AC-2** Ввод: `unknown-reference`, `duplicate`, `required`, `too-few`, `too-many` (60),
  `too-long` (4000), `not-allowed` (неизменный KSA без проверки). У `origin="solver"` нет
  `step_id`.
- **AC-3** Отметки: `step_source` / `ksa_source` / `human_checked` / `changed_in` по v4 §2.11.
  Перестановка полей не меняет. Смена `subject_version` — новая версия. Без изменений —
  `same-as-current` (поле `steps`).
- **AC-4** Семя: первая версия `solver` из `derived_steps`, затем `human`;
  `step_id = uuid5(STEP_NAMESPACE, kind:id:order)`.
- **AC-5** `step_history`: `added` / `changed` / `moved` / `removed`.
- **AC-6** Координатор: `current_solution(s)` отдаёт `SolutionView` адаптера как есть, ключи —
  входные `SourceRef`; неизвестный вид — `UnknownSolutionKind`. `solve`: предел — `DEADLINE`,
  исключение — `SOLVER_FAILED`. `enqueue_solve` — `NotImplementedError`.
  `from_payload(to_payload(r)) == r`; с `ml_context` — `ValueError`.
- **AC-7** `heads`, `latest_versions_for`, `heads_with_ksa` пакетом. Число запросов не зависит от
  числа владельцев.
- **AC-8** Только дописывание: `UPDATE` / `DELETE` / `TRUNCATE` — ошибка базы. Уникальности §3.1.
- **AC-9** Перенос: `human`-версий столько же, сколько правок; голова по 9 полям равна старому
  `effective_steps`.
- **AC-10** Повтор без новых правок ничего не добавляет. После отката цепочка продолжается. Правка
  к отсутствующему шагу — `raise`. Кандидаты с правками обоих кодов печатаются.
- **AC-11** После 0296 `INSERT` в `exam_solver_step_edit` — ошибка. Откат до 0295 снимает
  заморозку. Литерал пространства имён в миграции равен `STEP_NAMESPACE`.
- **AC-12** `reference_solution`: все 18 случаев §5.2 плана.
- **AC-13** Адаптер `exam_task`: `NO_SOLUTION` против `UNKNOWN_SOURCE`, шаги к чужой версии не
  подставляются, `solve` — `NOT_SUPPORTED`. Пакет равен поштучному чтению, число запросов —
  константа.
- **AC-14** На задаче с двумя совпавшими кандидатами очередь показывает того кандидата, которого
  отдаёт `reference_solution`.
- **AC-15** `GET /queue/steps`: есть `version_id` и `step_id`, нет `edit_id`. `POST` принимает
  `based_on` и `step_id`, отвечает 201 `{candidate_id, version_id, steps}`.
- **AC-16** 17 сценариев `test_steps.py` с прежним смыслом, кодами и полями;
  `same-as-current` — на поле `order`.
- **AC-17** Члены 409: `task_solution`, `exam_solver_candidate:<cid>`, UUID,
  `{version_id, steps}`.
- **AC-18** `GET /tasks/<id>/solution`: `reference`, `head` (`exam_task`),
  `for_current_revision`, `result_matches_answer` (`true` / `false` / `null`), `candidate_id`.
  GET в `api-problems.json` без 409.
- **AC-19** `POST`: таблица Р-1, строки 1–4. Журнал выбирает сервер под `lock_task`. Форма видела
  другой журнал — 409, `current_state` по виду журнала. Своё решение поверх кандидата — 409.
- **AC-20** Запись — список целиком, `ksa_id` у каждого шага (отсутствует = `null`).
  «Подтвердить» при тех же шагах — новая версия.
- **AC-21** Без права «Работа с экзаменами» — 403. Коды 422 — как в AC-2.
- **AC-22** `steps_reach_answer`, правило «одно число» (v6 §2.13): знаки сравнения и слова-основы
  дают «не сходится», `$…$` и LaTeX снимаются, берётся отрезок после последнего `=` / `≈`,
  команды без значения не совпадают. Держит контрактный тест T002 и случаи AC-12.
- **AC-23** Форма карточки заперта до чтения и пока GET в пути. Ответ к прежнему открытию —
  `stale` с тостом. Старый GET отбрасывается.
- **AC-24** 409 — слияние по шагам, правила 1–7 Р-6. При смене журнала черновик остаётся целиком,
  `step_id = null`, «сохранится как новые шаги». Перечитать не удалось — всё прежнее.
- **AC-25** Пределы 1–60 и 4000, текст обязателен. «Сохранить» неактивно без изменений.
  «Подтвердить к текущей версии» — только в строке 3. `ksa_id` шлётся у каждого шага.
- **AC-26** Показ: заголовок, источник, «проверено: кто, когда», «к текущей / прежней версии»,
  заметки об итоге и о прежнем решении методолога, «?» с текстом правила. Кнопки
  «выше» / «ниже». Без права — `NeedsRight`. Закрытие с правками — `ModalShell`. Без черновика
  раздел перечитывается после `load` карточки.
- **AC-27** Форма шага очереди при 409: слияние по полям (`mergeDraft`), отметка «этот шаг
  сменили».
- **AC-28** Форму закрыли до ответа — тост «Правка шага N не сохранена: …». Шаг пропал — заметка
  `role="status"`, список обновлён.
- **AC-29** Склейка KSA: версия `catalog_merge`, `ksa_source = catalog_merge`, остальное прежнее,
  `edited_by` — служебный. Оба вида владельцев, порядок замков `(kind, id)`. Конфликт — один
  повтор, затем громкий отказ.
- **AC-30** e2e Н-1 §5.3 (п. 1–7). **AC-31** e2e Н-1б §3 (сценарии 1–10), `showmigrations` без
  изменений. **AC-32** Полный прогон `courses` зелёный после вливания в ветку пайплайна; контракт

## 8. Разбор: конфликты, простой, что не получилось

### 8.1. Почему P ≈ 4, а не ≥ 8

Хребет T001 → T014 → T015 → T018/T020 — четыре звена по 16–24 веса, все deep. Что я проверял:

| Вариант | S | Цена |
|---|---|---|
| План как есть | 98 | — |
| `write_version` в К (К1 = deep L) | 86 (−12%) | К1 больше M (запрет §4); у deep L высокая доля отказов, а отказ К1 стоит всем |
| T020 и T018 по чтению и записи (4 задачи вместо 2) | 90 (−8%) | +2 задачи и +2 ревью; B-2 У1: мелкая нарезка проигрывает 6–10% |
| Ручки по журналу против подделки (фальшивый журнал) | 74 | расхождение сторон — вторая по частоте причина отказа у наставника; реальные замки не проверяются |

Ни один вариант не окупается. Честное утверждение — **«фича с новым ядром даёт P ≈ K, не 2K»**.
Норма P ≥ 2K в design §2.3 рассчитана на веер историй поверх готового ядра. Здесь ядро и есть
фича.

### 8.2. Где реальный выигрыш внутри задачи (позиция B, предложение к процессу)

Звенья хребта стоят на пути **вместе со своим ревью**: 5 звеньев × (8 мин ревью + 2 мин
вливания) = ~50 мин из 152. Ревью по ходу работы (по коммитам) только для задач пути — T001, T014,
T015, T018, T020 — сокращает ревью после сдачи до дельты (~3 мин). Модель (`f3b2.py`, `inline=1`):
до `[H]` при K = 4 — 152 → 139 (p = 0), 207 → 184 (p = 0.3), 234 → 203 (p = 0.43). Цена — +5
запусков ревью на фичу (~$7.5). Оговорка: в модели p на этих звеньях снижено ×0.7, а это **не
измерено**. Без этого снижения выигрыш — только латентность ревью, −8…−9%. В design.md этого пункта
нет; предлагаю его как опыт на этой фиче.

### 8.5. Замечания к design.md, найденные на этой фиче

1. Проба должна знать категорию **«хребет `[S]`»**. Иначе фича с новым ядром всегда красная по P
   и совет `⌊P⌋` вводит в заблуждение: здесь K = 3 медленнее K = 4 на 10–12%. Совет лучше считать
   моделью или границами, а не по `⌊P⌋`.
2. Нужно поле **`Вливание: вместе с …`**. Партия {T016, T018, T019} — не зависимость старта, а
   условие вливания. Без поля его держит только память координатора.
3. **Подготовка e2e — отдельная задача `[T]`.** Она снимает 20–35 мин с приёмок на пути и
   заполняет простой фазы К.
4. Критерий стека «срезов < 2K» считает срезы всей фичи. Здесь срезов 10 (≥ 8), а на хребте ширина
   1. Стек T015 → T018/T020 правило запрещает, хотя именно там слоты простаивают. Цифры:
   отказ T015 по смыслу шва задевает двух потребителей, а не весь веер. Предлагаю мерить «ширину в
   точке», а не по всей фиче, и проверить это на следующем круге.
