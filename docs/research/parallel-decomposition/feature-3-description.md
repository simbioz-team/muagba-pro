# Фича 3. Общий журнал решений задач по шагам (`task_solutions`) и раздел «Решение» в карточке задачи банка

Проект: «Наставник» (`/home/rustam/develop/simbioz_team/nastavnik_stage_1`). Ведёт сессия «банк
задач ЕГЭ» (модули `exam_*`, «Тренажёр ЕГЭ», staff `/exam`). В ADR-121 это пункт Н-1 вместе с
продолжением Н-1б (раздел «Решение» в карточке задачи банка). Потребитель контракта — соседняя
сессия пайплайна курса (её шаг 7 — пошаговые решения своих задач курса).

## Цель

Сейчас пошаговые решения есть только у решателя ЕГЭ: решатель пишет шаги кандидата, методолог
правит отдельные шаги в очереди (`ExamSolverStepEdit`). Курсу нужны такие же шаги и для задач банка,
и для своих задач. Нужен **один общий модуль** `courses/task_solutions/`, который не знает ни
экзамена, ни курса: реестр адаптеров по видам задач, координатор («дай решение этого источника к
этой версии», «реши»), журнал версий решения `SolutionVersion` с единственным писателем. Банк ЕГЭ
переводит на него правки шагов методолога и чтение эталонного решения; курс регистрирует свой вид
позже (вне этой фичи). Для методолога в staff — раздел «Решение» в карточке задачи банка: видно
происхождение шагов («решатель» / «методолог»), отметки «проверено» и к какой версии условия шаги
написаны; шаги можно добавлять, удалять, переставлять, править (текст, формула, результат, навык);
у задачи без решения — «Написать решение»; одновременная правка двух методологов — конфликт без
потери своих правок; без права — кнопки неактивны с подписью.

## Требования (сжато; полный текст — санированный план и контракт, см. «Документы»)

**Модуль и контракт `task_solutions`** (ярус 2; импортирует только `task_solving`, `helpers`,
`domain_errors`, ядро; не импортирует `exam_*`, `learning_tasks`, `billing`):
- контрактные типы (`types.py`): `SourceRef(kind, id, version)`, `SolutionRef`, `StoredStep` со
  стабильным `step_id`, `SolutionView`, `SolveRequest` (с `deadline_at`, `to_payload/from_payload`),
  `SpendContext.caller`, исходы и причины отказа;
- реестр адаптеров и координатор (`registry.py`, `services.py`): регистрация в `CoursesConfig.ready()`,
  чтение по источнику и версии (`current_solution(s)`), запрос решения синхронно и сигнатура
  асинхронного запроса (реализация асинхронного — вне фичи, Н-2), `latest_versions_for(pairs)`;
- журнал `SolutionVersion` (таблица `task_solution_version`): «правка — версия целиком», 409 при
  одновременной правке любого шага одного решения, `based_on`, замок журнала (`pg_advisory_xact`),
  порядок замков «строка владельца → замок журнала», склейка KSA каталога через адаптеры
  (`repoint_ksa`, новая версия `origin="catalog_merge"`), смена `subject_version` считается изменением;
- кто платит: при запросе решения курсом инициатор расхода — служебный пользователь платформы,
  запросивший — отдельным полем в строке расхода; модуль оплаты не меняется;
- коды отказов по реестру `config/response-codes.json` (новый код — запись реестра).

**Сторона банка ЕГЭ** (`exam_solver`, `exam_methodologist_queue`, `exam_tasks`):
- `exam_solver.reference_solution(exam_task_id, revision_id=None)` и пакетная версия по парам
  (задача, версия): решение задачи банка к версии условия; итог шагов сверяется с эталонным ответом —
  при расхождении курс шаги не получает;
- два вида владельца журнала: `exam_solver_candidate` (шаги кандидата решателя и правки методолога)
  и `exam_task` (решение методолога без кандидата);
- перенос существующих правок `ExamSolverStepEdit` в журнал миграцией данных (миграции 0295–0296;
  сверка «до/после»), правка шага в очереди методолога — через журнал; staff-форма правки шага
  работает на версии решения (`based_on`, 409 без потери правки);
- адаптер `exam_task` на чтение; `reference_solution` на журнале; очередь читает через него;
- ручки записи решения задачи банка методологом без кандидата (права «Работа с экзаменами»);
- запись решения — список шагов целиком, `ksa_id` у каждого шага (`null` — шаг без KSA); запись
  в журнал кандидата — одним писателем; GET без 409;
- правило сверки итога шагов с ответом эталона: «одно число» — узкое правило (знаки сравнения и
  слова-основы рядом с числом дают «не сходится»), правило показывается методологу во всплывающем
  окне по значку «?».

**staff `/exam`, карточка задачи банка** (`services/staff/app/(staff)/exam/`):
- раздел «Решение» в `TaskDrawer`: показ, «Подтвердить к текущей версии», перечитывание;
- модуль формы решения: клиент ручки, правила шага значением, редьюсер списка;
- правка списка шагов, слияние черновика по шагам при 409, подтверждение закрытия, «Отмена» по
  последнему чтению;
- хвосты формы правки шага в очереди методолога (несохранённая правка закрытой формы, пропавший шаг);
- показ шагов ученику тренажёра **не делается** (решение владельца: «не показывать пока»).

## Критерии приёмки

- Модульные тесты по §5.2 санированного плана; изменения API очереди — §5.1 (явно перечислены).
- e2e на стенде `trn-*` (:8090, копия БД `trainer_verify`) по §5.3 плана: правка шага методологом на
  журнале, 409 у второго методолога, перенос старых правок без потерь, решение задачи банка без
  кандидата, выдача решения курсу и тренажёру через `current_solution` / `reference_solution`
  (проверка в shell).
- e2e раздела «Решение» на `trn` по §3 санированного Н-1б: решение без кандидата; шаги доступны курсу и
  тренажёру через выдачу решения; два методолога одновременно — второй видит конфликт; без права —
  кнопки неактивны; миграций у staff-части нет (`showmigrations` до и после без изменений).
- Полный прогон тестов `courses` зелёный после вливания в ветку пайплайна курса; контракт передан
  соседней сессии и согласован.
