# Команда A, круг 1: разложение по контрактам и вертикальным срезам

Позиция: ширину плана задаёт не оркестратор, а форма графа. Зависимость
«B ждёт код A» заменяется зависимостью «B ждёт интерфейс A». Интерфейсы
(схемы API, поля сущностей, миграции, ключи словарей, коды ответа, порты с
заглушками) делает одна короткая фаза **К** (контракт). После неё срезы
идут веером, каждый в своих файлах, а цикл ревью перестаёт держать слот
исполнителя.

Модель проверки — `sim/sim_a.py` рядом с этим файлом (дискретная
симуляция, 200–300 прогонов, длительности из наблюдений 20–24.11).

## 1. Почему именно контракт (основания)

| Наблюдение у наставника | Что его вызывает | Что делает контракт |
|---|---|---|
| Занято 2.1–2.4 из 4 исполнителей | граф-лестница «модели → сервисы → эндпоинты → UI», которую предписывает шаблон Spec Kit ([tasks-template.md](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)) | слои уходят в К, а в срезах остаётся по одному уровню. Симуляция слоёв дала **2.27** занятых, то есть модель откалибрована по факту |
| 16 из 19 отказов при 4 исполнителях — пересечение с соседней задачей | две задачи добавляют поле в одну сущность или растят одну меру (случай T019 ∥ T020, `task_pairs.py`) | всё общее (сущность, мера, порт, миграция, ключ) имеет одного владельца, задачу К. У среза строк `Сущность:`, `Мера:`, `Миграция:` нет по определению |
| Отказы по расхождению сторон (сервер/клиент, запись/чтение) | каждая сторона угадывает форму данных сама | обе стороны проверяются против одной схемы контрактными тестами из К ([Fowler, CDC](https://martinfowler.com/articles/consumerDrivenContracts.html), [Pact](https://pact.io/)) |
| Семантические конфликты до 97% на задачах со сменой интерфейса ([arXiv 2609.25396](https://arxiv.org/abs/2609.25396)) | интерфейс меняют посреди волны | интерфейс заморожен до волны, поправка идёт только добавлением и по протоколу (§6) |

Источники приёма: Google, «слои развязываются proto signature or API stub»
([small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html));
Spec Kit, «Foundational BLOCKS all user stories», поэтому фаза обязана быть
маленькой; wshobson `/team-feature`, где файл типов принадлежит лиду
([SKILL.md](https://github.com/wshobson/agents/blob/main/plugins/agent-teams/skills/parallel-feature-development/SKILL.md));
Shape Up, вертикальные scopes ([гл. 12](https://basecamp.com/shapeup/3.3-chapter-12)).

## 3. Форма задачи

```markdown
- [ ] T014 [V] История 2: экспорт банка заданий в CSV
  Срез: US2/сценарий «учитель выгружает банк»
  Контракт: C1 (GET /api/banks/{id}/export, схема ExportRow), C2 (порт BankReader)
  Файлы: apps/banks/export/views.py, apps/banks/export/csv.py, web/src/banks/ExportButton.tsx, tests/banks/test_export.py
  Зависит от: C1, C2
  Готово-когда: test_export_roundtrip, test_export_empty_bank, ExportButton.spec — зелёные; без кода среза краснеют
  Тест-группа: banks
  Размер: S (≤ ~300 строк диффа, один запуск исполнителя)
```

Виды задач: `[K]` — контракт, `[V]` — срез, `[H]` — хвост, `[S]` —
последовательная (только с полем `Почему не срез:`).

Обязательно для `[V]`:
- `Контракт:` называет швы, которые срез **читает**. Менять их срез не может;
- `Файлы:` — только свои. Общие разрешены лишь из `shared` в
  `.claude/pair-rules.txt` (регистрация, генерируемое);
- полей `Сущность:`, `Мера:`, `Миграция:` нет. Если они понадобились, это
  шов, и его место в К;
- `Готово-когда:` перечисляет тесты по именам и требует, чтобы они
  «краснели без кода среза» (проверка удержания, §7). Это прямой ответ на
  отказ «тест ничего не держит» и на «незакрытый пункт задачи».

Поля `Файлы:`, `Мера:`, `Сущность:` уже читает `task_pairs.py`, новое
добавляется только `Контракт:`, `Готово-когда:` и вид в скобках.

## 4. Правила зависимостей

1. Ребро бывает трёх видов: **по контракту** (К → V, норма), **по коду**
   (V → V, исключение), **по ресурсу** (`serial` из `pair-rules.txt`).
2. Ребро «по коду» записывается с полем `Почему не по контракту:`.
   `architect` обязан сначала спросить себя, можно ли написать B против
   интерфейса A с заглушкой. Если можно, интерфейс уходит в К, а ребро
   превращается в «по контракту».
3. Задачи К между собой параллельны, у каждой свои швы. Цепочка К → К
   допустима только для генерации (схема → клиент), и тогда её делает одна
   задача.
4. Срез не зависит от хвоста, хвост зависит от срезов. Приёмка зависит
   только от срезов своей истории.
5. Внутри истории нет слоёв. Если история не помещается в один срез, она
   режется по сценариям (каждый насквозь), а не по слоям.

## 5. Что проверяется на плане до старта (`plan_width.py`)

Скрипт на python3 читает `tasks.md` тем же разбором, что `task_pairs.py`.
Это отчёт, а не гейт: по CLAUDE.md базы новый гейт — ломающее изменение.
Красное в отчёте — повод `architect` переложить план, а не запрет запуска.

| Мера | Порог для N исполнителей | Зачем |
|---|---|---|
| Критический путь (в задачах, К и deep с весом 1.6) | ≤ 4 звеньев: К → V → (V) → Х | быстрее цепочки фича не кончится ([CPM](https://en.wikipedia.org/wiki/Critical_path_method)) |
| Средняя занятость при списочном расписании на N слотов в фазе веера | ≥ 0.8·N | ширина, ради которой всё затевается |
| Доля фазы К в оценке фичи | ≤ 20% | Foundational блокирует всё |
| Пересечение `Файлы:` у задач без пути между ними | 0, кроме `shared` | правило базы «общие файлы одновременно не берутся» становится проверяемым для всего плана, а не только для пары |
| `[V]` с `Сущность:` / `Мера:` / `Миграция:` | 0 | шов вне контракта |
| Шов из `contracts.md` без владельца К или без потребителя | 0 | висящий или лишний контракт |
| Рёбра V → V без `Почему не по контракту:` | 0 | |
| `[V]` без `Готово-когда:` с именами тестов | 0 | |

Вывод — одна таблица: N, путь, занятость, нарушения. Считается сразу для
N = 3, 4, 5. По ней видно, где дальше расширять бесполезно: «Three focused
teammates often outperform five scattered ones»
([Agent Teams](https://code.claude.com/docs/en/agent-teams)).

## 6. Поправка контракта посреди волны

- Исполнитель среза, которому не хватило шва, **не правит контракт в своей
  ветке**. Он докладывает «контракт недостаточен: шов, чего нет» и
  продолжает то, что от шва не зависит.
- Координатор заводит `K-amend` (deep), **только добавление**: новое поле,
  новый метод, новый код. Переименование и удаление идут через выведение,
  как в ADR-0019. Поправку вливают раньше срезов в полёте.
- Всем срезам, у которых этот шов в `Контракт:`, приходит одно сообщение
  «шов изменён, rebase» — по правилу «итогом, а не потоком». Уведомление
  о соседнем изменении восстанавливает 82% прогонов
  ([arXiv 2609.25396](https://arxiv.org/abs/2609.25396)).
- Ломающая поправка (надо менять тип, а не добавлять) останавливает
  потребителей шва. Это событие для журнала: план был неверен, и `architect`
  разбирает, почему ревью шага 5 его пропустило.

## 7. Цикл «исполнитель → ревью → правки» без цепочки

Сейчас слот исполнителя и зависимость держатся весь цикл, до вливания.
Предлагается:

1. **Сдал — свободен.** Исполнитель после гейта `check.sh` берёт следующий
   готовый срез. Доработка — это **новый запуск** (правило базы уже велит
   так делать: кэш живёт 5 минут, а доработка начинается позже) с находками,
   веткой и прошлым докладом. Она встаёт в общую очередь **первой** и
   достаётся любому свободному исполнителю. Слот больше не ждёт ревьюера.
2. **Механику ревьюер не проверяет.** Гейт уже держит `check.sh`. Добавляется
   **проверка удержания**: тесты из `Готово-когда:` прогоняются на дереве,
   где код среза откатан (`git checkout <HEAD-K> -- <не-тестовые Файлы:>`),
   и обязаны покраснеть. Исполнитель прикладывает вывод к сдаче, ревьюер его
   читает, а не повторяет. Так ловится «тест, который ничего не держит»,
   причём механически.
3. **Ревью уже, потому что контракт ревьюирован.** Ревьюер среза сверяет
   три вещи: соответствие швам из `Контракт:`, закрытие `Готово-когда:` и
   логику поведением. Расхождение сторон и пересечение с соседом закрыты
   формой плана; соседние ветки ему по-прежнему называются.
4. **Три ступени вердикта:** «можно сливать», «можно сливать, хвост» и
   «нельзя сливать». Средняя ступень значит, что находки не про
   корректность и требования, а дословно уходят в задачу `[H]`. Это Google
   «LGTM with comments» и Nit/Optional
   ([comments](https://google.github.io/eng-practices/review/reviewer/comments.html)),
   а также `deferred-work.md` из [bmad-loop](https://github.com/bmad-code-org/bmad-loop).
   Предел — два круга, как уже записано в базе.

Модель (§10) показывает, что п. 1 даёт выигрыш только вместе с широким
графом: на лестнице освобождённому исполнителю нечего брать, и время то же
(345 мин в обоих режимах).

## 8. Слияния, тесты, CI, документы

- **Конфликтов текста нет по построению**, потому что `Файлы:` срезов не
  пересекаются (это проверено пробой). Остаётся `shared` (регистрация уже
  сделана в К заглушками, срез только заменяет тело) и генерируемое,
  которое перегенерируют, а не сливают руками.
- **Поезд вливаний.** Срезы, прошедшие ревью, вливаются в ветку фичи
  `--ff-only` по одному после rebase (rebase тривиален). Пушится и гоняется
  CI **партией по 3–4 вливания**, а не на каждое: 22 среза × 15–28 мин на
  3 раннерах — это ~160 минут CI, столько же, сколько вся фича. Партиями
  выходит 6 прогонов. Красная партия делится пополам (бисекция по Refinery
  из [Gas Town](https://github.com/gastownhall/gastown)). Доказательством
  для каждой задачи остаётся зелёный полный `check.sh` у ревьюера на коммите
  сдачи (правило базы «полная проверка — один раз на задачу»).
- **Тест-группы.** `Тест-группа:` у среза даёт проекту основание сузить
  отпечаток: К меняет `services/` один раз, срезы кладут код в свои модули.
  Сейчас любая правка `services/` сбрасывает все группы django, поэтому
  проекту стоит размещать код срезов вне `services/` или разбить отпечаток
  по пакетам. Это решение проекта, а не базы: база только меряет.
- **Документы.** Документ среза (раздел фичи, описание эндпоинта) пишется в
  `Файлы:` среза, в свой файл. Общие реестры (`INDEX.md`, `TAGS.md`,
  журнал) генерируются или пишутся хвостом после вливаний. Это правило
  базы «журнал и договорённости — после вливания обеих», расширенное на N.
- **Миграции.** Все миграции фичи живут в К, поэтому цепочка ревизий
  линейна и двух голов не бывает.

## 9. Что меняется в базе (поверх muagba)

- `template/AGENTS.md`: правило «парами, не больше двух» → «до N, если
  `plan_width.py` не нашёл пересечений в наборе». `task_pairs.py merge`
  обобщается на N веток: пробное слияние всех в полёте при каждой сдаче.
  Правило «`tasks.md` пишется под пары» → «под контракт и срезы» (§3–4).
- `architect.md`: шаги 1–3, правило «ребро по коду — с обоснованием».
- `implementer*.md`: «контракт недостаточен» — доклад, а не правка;
  проверка удержания в доказательстве сдачи.
- `reviewer.md`: линза «хватит ли срезам» на ревью К; три ступени вердикта;
  механику не повторять.
- `scripts/plan_width.py` + случаи в `scripts/tests/`. Сам скрипт — отчёт,
  не гейт, поэтому в 0.x он патч, а не минор.

Из готового берём: формат и фазы Spec Kit (уже стоит у проектов),
`conflicts_with` из [CCPM](https://github.com/automazeio/ccpm) (у нас это
`Файлы:` + `serial`), владение файлами и контракт лида из wshobson, предел
кругов и журнал отложенного из bmad-loop, бисекцию очереди из Gas Town.
Целиком не годится ни один (research.md §4): никто не меряет ширину.
Agent Teams не берём зависимостью: функция экспериментальная, а координатор
базы уже раздаёт задачи.

## 10. Прогноз (модель `sim/sim_a.py`)

Допущения: 22–28 задач; исполнитель 10 мин (deep ×1.6), ревью 8, доработка
7, вливание 2, разброс 0.7–1.4; ревьюеров 3–4.

| План | Режим ревью | N=4 | N=5 | Занято в среднем |
|---|---|---|---|---|
| Слои (Spec Kit как есть) | слот держится до вливания (сейчас) | 345 мин | 345 мин | 2.27 (факт: 2.1–2.4) |
| Слои | конвейер (§7) | 345 | 345 | 1.11 |
| К цепочкой (К1→К2) + срезы + 2 хвоста | конвейер, p=0.3 | 254 | 252 | — |
| **К параллельно (К1∥К2), регистрация в К, 1 хвост** | конвейер, p=0.3 | **186 (−46%)** | 177 | ~4 в веере, 2.1 за всю фичу |
| то же | конвейер, p=0.15 | **153 (−56%)** | 146 | |

Выводы модели:
- выигрыш дают **ширина вместе с конвейером ревью**, по отдельности почти
  ничего. Конвейер на лестнице бесполезен, широкий граф с блокирующим ревью
  даёт только −11…−18%;
- после расширения длительность определяют **последовательные звенья
  вокруг веера**: К и хвост. Цепочка К1→К2 и два хвоста стоили 70 минут
  (254 против 186). Отсюда правила «К параллельны между собой» и «один
  хвост»;
- N=5 против N=4 даёт всего −5%: веер из 22 срезов по 10 минут
  выбирается четырьмя быстрее, чем кончаются К и хвост. **Пятый исполнитель
  окупается только на фичах от ~30 срезов**;
- падение доли доработок с 30% до 15% (за счёт удержания и сужения ревью)
  стоит ещё ~33 минуты и важнее пятого исполнителя.

Чего модель не видит: смысловую ошибку контракта (§6, ломающая поправка
отбрасывает потребителей назад) и CI, если его не перевести на партии.

## 11. Где нас будут бить и ответ заранее

- **«Контракт заранее — это водопад, архитектор не угадает».** Угадывать
  надо только швы, а не реализацию. Швы и так проявляются в `plan.md`
  Spec Kit (раздел contracts/data-model). Ошибка шва дешевле в К (одна
  задача), чем в N срезах, где сейчас и случаются 42–44% отказов. Поправка
  только добавлением держит неугадку обратимой.
- **«Фаза К блокирует всех, а это та же лестница».** Да, поэтому порог
  ≤ 20% и параллельность К. Модель: К на ~16% длительности.
- **«Агентские срезы всё равно лезут за `Файлы:`»** (narta T019 ∥ T020).
  Выход за `Файлы:` у среза — находка ревью и признак дырявого контракта,
  разбираемый на шаге 5. Пробное слияние N веток при каждой сдаче ловит
  остаток за секунды.
- **«Не все фичи режутся по контракту»** (алгоритм, рефакторинг, один
  сложный модуль). Для них есть вид `[S]` с `Почему не срез:`, а проба
  честно показывает узкий граф. Тогда N=2 и ставка на deep-исполнителя:
  параллельность здесь не цель (Cognition, [Don't build multi-agents](https://cognition.com/blog/dont-build-multi-agents)).
