# `setup_state.py` — проект

Скрипт, по которому конвейер понимает, где остановилась настройка. Гейты —
в `docs/gates.md`, этапы и задачи — в `docs/pipeline.md`, вопросы к человеку —
в `docs/interview.md`.

Живёт в плагине: `plugins/muagba-base/scripts/setup_state.py`.

## Назначение

Ответить на один вопрос: **с какого места продолжать.**

Из этого следует всё остальное. Состояние не хранится, а выводится: скрипт
прогоняет пробы по репозиторию и называет первый этап, который не закрыт.
Прерывание настройки поэтому ничего не стоит — при следующем запуске состояние
считается заново.

## Чего он не делает

- **Не чинит.** Нашёл незакрытую пробу — сказал, что не так и что сделать.
  Правки вносит человек или скил, но не скрипт.
- **Не пишет в репозиторий.** Единственный файл, который он трогает, —
  `.claude/setup.json`, и только по явной команде `confirm`, `unconfirm`,
  `trait`.
- **Не решает за человека.** Признак проекта («есть ли UI») не угадывается по
  коду: неверная догадка молча пропустит гейт, который был нужен.

Проба — чистая функция от состояния репозитория. Проба, которая что-то меняет,
— ошибка проектирования.

## Четыре вердикта

Двух состояний не хватает, и это выяснилось на условных пробах.

| Вердикт | Что значит | Когда |
|---|---|---|
| `ok` | пройдено | машинная проба зелёная либо человеческая подтверждена |
| `fail` | не пройдено | с причиной и указанием, что сделать |
| `skip` | неприменимо | признак объявлен и говорит, что пробы нет смысла, либо у пробы нет предмета |
| `unknown` | **не решено** | условная проба, а признак не объявлен |

«Нет предмета» — узкая лазейка, и её надо держать узкой: она разрешена только
пробам, которые проверяют **оформление необязательного артефакта**.
`entry.sources` смотрит, у всех ли файлов в `docs/sources/` заполнен `origin`;
источников нет — проверять нечего. Проба, которая требует, чтобы артефакт
существовал, так пропускаться не может, иначе `skip` станет способом закрыть
любой этап, ничего не сделав.

`unknown` — отдельный вердикт намеренно. Молча считать непонятное
пройденным — врать; считать непройденным — блокировать проект, которому
проба не нужна. Правильный ответ — спросить человека, и для этого нужен
отдельный вердикт.

## Когда этап закрыт

```
этап закрыт = нет ни одной пробы со статусом fail или unknown
```

`skip` не мешает. Машинные пробы пересчитываются каждый запуск, поэтому
подтверждение само по себе этап не закрывает: удалили `check.sh` — Э6 снова
открыт, хотя подтверждение на месте.

**Первый незакрытый этап** — тот, с которого продолжают. Пробы всех этапов
прогоняются всегда, а не до первого провала: часть поздних этапов может быть
уже сделана, и это надо видеть. Исключение — дорогие пробы, см. ниже.

## Реестр проб

Одна структура на пробу, в одном месте:

```python
Probe(
    id="product.antigoals",          # стабильный идентификатор
    stage="Э2",
    title="граница объёма задана",
    kind=MACHINE,                    # MACHINE | HUMAN
    needs=None,                      # имя признака для условной
    cost=CHEAP,                      # CHEAP | EXPENSIVE
    watch=["docs/product/mission.md"],  # для HUMAN: от чего протухает
    fills=("docs/product/mission.md", "Чего продукт НЕ делает"),
    run=probe_antigoals,             # (ctx) -> Verdict
)
```

`fills` — то, чего проба требует, названное так же, как это называет банк
вопросов. Поле существует ради сверки полноты: у каждого требуемого раздела
обязан быть вопрос, которым его заполняют. Без него дыра выглядит как красная
проба без подсказки, что отвечать.

`fills=None` — у пробы нет адресата среди вопросов: она закрывается действием
агента, а не ответом человека. Таких много и это нормально: `git.repo`,
`entry.plugins`, самотесты хуков. Спрашивать «завести ли репозиторий» незачем.

`id` попадает в `.claude/setup.json` и в вывод, поэтому переименование —
ломающее изменение: старые подтверждения осиротеют.

### Согласованность со спецификацией

`docs/gates.md` написан прозой и остаётся источником для человека. Код —
источник поведения. Чтобы они не разошлись, есть режим `--check-spec`: он
сверяет **множество идентификаторов** в коде с тем, что перечислено в
таблицах `gates.md`, и ругается на расхождение в любую сторону.

Генерировать `gates.md` из кода не стали: прозаические объяснения «почему
именно эта проба» в код не помещаются, а без них таблица превращается в
список без смысла. Сверка множеств даёт ту же гарантию дешевле.

### Полнота банка вопросов

`--check-questions` сверяет две стороны:

```
fills машинных проб   ⊆   цели из «Заполняет:» банка
```

Обратное включение не требуется: вопрос может заполнять раздел, который
проверяет человеческий гейт, а тот смотрит на документ целиком. Что показала
первая такая сверка — в `docs/interview.md`, раздел «Что показала первая
сверка».

Оба режима сверки — про согласованность базы с самой собой. Пробами проекта
они не являются и в таблицу гейтов не входят: проверять их место — CI
репозитория базы.

## Файл состояния

`.claude/setup.json` — единственное, что хранится. Всё остальное выводится.

```json
{
  "version": 1,
  "traits": {
    "ui": true,
    "storage": false,
    "remote": true
  },
  "confirmed": {
    "check.red": {
      "at": "2026-09-20",
      "note": "сломал парсер дат, тесты покраснели, откатил",
      "fingerprint": { ".claude/check.sh": "a1b2c3d4" }
    }
  }
}
```

**Признаки объявляет человек**, а не скрипт. Их немного:

| Признак | Что включает | Чем объявляется |
|---|---|---|
| `ui` | `env.browser-cfg`, `env.browser-works`, `check.e2e` | вопрос В5.1 |
| `storage` | `env.seed` | вопрос В4.5 |
| `remote` | `git.protected` | вопрос В0.1 |

Признак не объявлен — соответствующие пробы дают `unknown`, и конвейер
спрашивает.

Признаки — единственные ответы человека, которые хранятся отдельно от
документов, и хранятся потому, что их читает машина. Всё остальное живёт в
документах рамок; отдельного хранилища ответов нет (`ADR-0006`). Отсюда
правило, удерживающее таблицу от разрастания: **признак заводится только
тогда, когда от него зависит машинная проба.** Условие вопроса, от которого не
зависит ни одна проба, пишется прозой и разбирается агентом.

Тот же признак гасит и пробу, и вопрос, так что они выключаются согласованно:
нет интерфейса — не спрашиваем про браузерные сценарии и не требуем их.

## Протухание подтверждений

Подтверждение — свидетельство о факте, случившемся в прошлом. Оно устаревает,
когда меняется то, о чём свидетельствовали.

Человеческая проба объявляет `watch` — файлы, от которых зависит её
утверждение. При `confirm` в подтверждение записывается их отпечаток. При
следующем прогоне отпечаток пересчитывается:

```
совпал      → ok
не совпал   → fail: «check.sh изменился с 2026-09-20, подтверждение устарело»
```

Без этого `check.red` означал бы «когда-то проверка краснела», а не «проверка
краснеет». Разница существенная: `check.sh` переписывают, и переписанная
версия вполне может перестать падать.

Файл из `watch` исчез — то же самое: подтверждение недействительно.

## Дорогие пробы

Возобновление вызывается часто, и проверка состояния обязана быть быстрой.
Приём «проверять дешёвый след вместо дорогого действия» закрывает почти всё
(см. `gates.md`), но одна проба неустранимо дорогая: `check.green` — это и
есть полный прогон проверки проекта.

Правило: **дорогая проба прогоняется только для этапа, который сейчас
проходят**, и для всех остальных показывается как `· не проверялась`. Флаг
`--full` заставляет прогнать всё, `--fast` — не прогонять дорогое вовсе.

Значки: `✓` закрыт, `✗` есть провалы, `?` есть нерешённое, `·` не проверялся.

Каждая незакрытая проба печатает **что сделать**, а не только что не так. Это
то же правило, по которому написаны ошибки хуков.

### Скилу

`--json` даёт одну структуру:

```json
{
  "next_stage": "Э2",
  "stages": [
    { "id": "Э2", "title": "Продуктовая рамка", "closed": false,
      "probes": [
        { "id": "product.antigoals", "verdict": "fail",
          "detail": "раздел антицелей пуст",
          "fix": "docs/product/mission.md, раздел «Чего продукт НЕ делает»" }
      ] }
  ],
  "undeclared_traits": ["ui"],
  "orphan_confirmations": []
}
```

`next_stage` — `null`, когда закрыты все.

## Команды

```
setup_state.py                      таблица и куда продолжать
setup_state.py --json               то же для скила
setup_state.py --stage Э6           только один этап, дорогие пробы включены
setup_state.py --full               прогнать всё, включая дорогое
setup_state.py --fast               пропустить дорогое
setup_state.py --check-spec         сверить набор проб с docs/gates.md
setup_state.py --check-questions    сверить банк вопросов с целями проб

setup_state.py confirm <id> [--note "..."]
setup_state.py unconfirm <id>
setup_state.py trait <имя>=<true|false>
```

`confirm` отказывается подтверждать пробу, у которой `kind=MACHINE`: машинную
пробу нельзя закрыть словом.

## Как этим пользуется `/setup-project`

1. Запускает `--json`.
2. Читает `next_stage`. Пусто — настройка закончена, сказать об этом.
3. Есть `undeclared_traits` — спросить про них раньше всего: иначе часть
   этапов будет висеть в `unknown` до конца. Вопросы для них помечены в банке
   полем «Даёт признак».
4. Провести этап `next_stage` по его задачам из `pipeline.md`, а вопросы взять
   из `questions/NN-*.md`: отбросить те, чьё условие не выполняется, по
   остальным сначала поискать ответ в `docs/sources/`, показать найденное на
   подтверждение и спросить только недостающее (`docs/interview.md`).
5. Перезапустить `--json`. Этап не закрылся — показать оставшиеся пробы и не
   идти дальше.

Скил **не решает сам**, пройден ли этап. Это решает скрипт, и только он.

## Отказоустойчивость

| Что случилось | Как ведёт себя |
|---|---|
| проба упала с исключением | `fail` с текстом ошибки; остальные пробы прогоняются |
| проба зависла | таймаут 10 секунд, дорогие — 600; дальше `fail` |
| `.claude/setup.json` не разбирается | назвать файл и строку, ничего не перезаписывать |
| подтверждение на несуществующую пробу | показать как осиротевшее, предложить `unconfirm` |
| запуск из рабочего дерева | корень ищется от `cwd`, как в хуках |
| запуск вне проекта | сказать, что не найден `.git` или `.claude/`, и выйти |

Ни один отказ не должен ронять весь прогон: смысл скрипта в том, чтобы
показать картину целиком, а картина с одной дырой полезнее отсутствия
картины.

## Открытое

- **Пробы `cycle.*` проверяют наличие разделов в документах.** Это слабо:
  раздел может быть на месте и пуст по смыслу. Сильнее не сделать машиной —
  вероятно, часть из них должна стать человеческими.
- **`roles.split`** — «у проверяющего нет инструментов правки» — читается из
  фронтматтера роли, но роль может прийти из плагина, где её не поправить.
  Что делать в этом случае, не решено.
